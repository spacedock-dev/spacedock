The FO, knowing the file exists by name because its own contract just named it, does what a competent agent does when a known file isn't where it looked: it searches the filesystem for it (`find`, `grep -r`) — the exact "contract-file find-hunt" failure sub-class documented across sc5's 16-instance ledger (spacedock-dev/spacedock).

The evidence is a precise 1:1 match, not a guess: every hunt instance in that ledger targets one of the three bare-path files (`fo-merge-core.md`, `fo-dispatch-core.md`/`claude-fo-dispatch.md`, `fo-smallest-sufficient-mechanism.md`) or greps the plugin skill tree those files live in — never a `Skill()`-addressed load point. The contract's existing anti-hunt rule ("do NOT broad-search the filesystem to hunt one," Startup step 2) covers only the zero-discovery-workflow case; there is no equivalent rule at the Deferred load points section forbidding a hunt for a *reference file*.

## Proposed approach

**Scope: Move 3 — hand the FO the entity stub template at the surface it already consults, and make the post-`new` commit action self-evident.** This is a code change to `spacedock new`'s own output, NOT more contract prose: Move 1 already showed a prose nudge under-delivers on this scenario, and the transcripts show the FO already reaches the contract prose and hunts anyway. It targets the directly-evidenced hunt — the FO seeks a copyable stub and a clear commit next-step, and the tool provides neither.

**The change (two small, same-lever edits to the `new` command's output).**

1. **`spacedock new --help` gains a body-shape description + a copyable stub template block** (`internal/cli/help.go`, the `new` long-help renderer). The FO runs `new --help` in 4/4 read `filing` transcripts, so this intercepts the hunt at the exact surface the FO consults.
2. **`spacedock new`'s empty/malformed-stdin error prints the same stub template** (`internal/status/new.go`, the two `errExit` paths: the empty read and the "no frontmatter found" case). A FO that pipes nothing or a malformed stub is shown the exact shape instead of being sent hunting.

Both also state the **post-`new` commit action per root layout**, killing the secondary single-root commit hunt: `new` writes but does not commit; on split-root run `spacedock state commit SLUG` (and push); on single-root the entity is written into the working tree for the next state-transition commit. (Implementation confirms whether `new` can cheaply detect the root layout from the discovered README; if not, the help/error prose states both cases and `new`'s success line gives a generic "commit the new entity" reminder — an implementation detail, not a new mechanism.)

**Before/after wording** (user-visible CLI output, so exact wording per the stage-def rule):

BEFORE — `spacedock new --help` long body (`internal/cli/help.go`) ends the description at the auto-discovery sentence, then jumps to `Flags:` / `Examples:`; nothing states what the stdin body must contain.

AFTER — insert a body-shape paragraph and a `Body template` block after the auto-discovery sentence and before `Flags:`, and add a piped example:

> The stdin body is a complete entity stub: YAML frontmatter with a `title` and the
> workflow's initial `status`, with `id` OMITTED (new mints and stamps it — a body
> that declares its own `id` is rejected), then a blank line, then a one-paragraph
> description. new writes the file but does NOT commit: on a split-root workflow run
> `spacedock state commit SLUG` (and push) afterward; on a single-root workflow the
> entity is written into the working tree for your next state-transition commit.
>
> Body template (pipe this on stdin; fill the angle-bracket fields, id omitted):
>   ---
>   title: <one-line title>
>   status: <initial stage from the workflow README, e.g. backlog>
>   ---
>   <one-paragraph description of the work>
>
> Examples:
>   spacedock new my-task < body.md
>   printf '%s\n' '---' 'title: Wire the thing' 'status: backlog' '---' 'Wire it up.' | spacedock new my-task
>   spacedock new --folder my-task < body.md
>   spacedock new my-task --workflow-dir docs/dev < body.md

AND — `internal/status/new.go`'s empty-read and "no frontmatter found in --new entity body (stdin must begin with ---)" `errExit` messages gain the same `Body template` block, so a malformed pipe is shown the shape rather than only the terse "stdin must begin with ---".

**Doc diff (user-visible CLI change → required per the stage-def).** The docs-site command reference carries a one-line `new` entry; expand it to point at the template. `docs/site/reference/command-reference.md` (line ~47):

BEFORE:

AFTER:
