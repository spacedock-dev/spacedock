The FO's boot-resident contract (`skills/first-officer/references/first-officer-shared-core.md`, `## Deferred load points`, lines ~32-40) names five deferred references that load via `Skill(skill="spacedock:...")` — cwd-independent, resolved through the Claude Code plugin/skill registry regardless of the FO's working directory. Three more — `references/fo-dispatch-core.md`, `references/fo-merge-core.md`, and `references/fo-smallest-sufficient-mechanism.md` (plus the runtime adapter files, e.g. `claude-first-officer-runtime.md`, `claude-fo-dispatch.md`) — are named the same way in prose but load via a bare relative path. When the FO's cwd is not the skill's own install directory (as in the live-CI test harness, where `cmd.Dir` is set to the scenario's fixture root), a bare read of `references/fo-dispatch-core.md` resolves against cwd and fails to find the file. The FO, knowing the file exists by name because its own contract just named it, does what a competent agent does when a known file isn't where it looked: it searches the filesystem for it (`find`, `grep -r`) — the exact "contract-file find-hunt" failure sub-class documented across sc5's 16-instance ledger (spacedock-dev/spacedock).

The evidence is a precise 1:1 match, not a guess: every hunt instance in that ledger targets one of the three bare-path files (`fo-merge-core.md`, `fo-dispatch-core.md`/`claude-fo-dispatch.md`, `fo-smallest-sufficient-mechanism.md`) or greps the plugin skill tree those files live in — never a `Skill()`-addressed load point. The cycle-1 implementer of sc5 independently documented the same mechanism verbatim in a detector's doc comment (`broad_search_detect_impl_test.go`) and then built a test-only detector for the symptom instead of fixing the cause — the detector (`detectBroadSearchAtBoot`) lives in a `_test.go` file and grades CI streams after the fact; it does not gate a real production FO's behavior. The contract's existing anti-hunt rule ("do NOT broad-search the filesystem to hunt one," Startup step 2) covers only the zero-discovery-workflow case; there is no equivalent rule at the Deferred load points section forbidding a hunt for a *reference file*.

Two candidate fixes, smallest-sufficient first (full analysis and citations available from the opus advisory consultation this entity was split from — ask the FO session that filed this, or re-derive from sc5's entity body and the FO contract files directly):

- **Move 1 (low risk, additive prose).** Add a rule to `## Deferred load points` symmetric to the existing zero-discovery one: reference files load from the skill's own install directory, never relative to the FO's working directory; never hunt the filesystem for a contract/reference file known by name; if a reference read fails, stop and report the unresolved path rather than searching for it.
- **Move 2 (higher risk, needs its own spike before ideation commits to it).** Unify addressing — promote `fo-dispatch-core.md`/`fo-merge-core.md`/`fo-smallest-sufficient-mechanism.md` to `Skill()`-addressed modules (none of the corresponding skills exist today — only `fo-dispatch-recovery`, `fo-status-viewer`, `fo-write-core`, `present-gate`, `feedback-rejection-flow` do), or add an explicit skill-root path anchor the FO prepends to a bare read. This touches the boot → dispatch → merge path, the most load-bearing sequence in the system, and must not be a drive-by edit — spike it first per the workflow's own Probe policy (launch one FO under `--plugin-dir` with cwd at a fixture, trigger a dispatch, and directly observe how the reference resolves) before committing to a specific mechanism.

Value measure for whoever picks this up: the live find-hunt *rate* on the sonnet claude-live lane trending toward zero — the end-value sc5 could never reach because sc5 was scoped, by its own Proposed approach, to test-harness/fixture edits only ("all edits are to `internal/ensigncycle/*_test.go`... No doc diff required"). That scope boundary is why two rejection cycles on sc5 kept routing back to "add more harness" for a behavior whose root cause was always in the contract, not the tests.

## Proposed approach

**Scope: Move 1 only — the additive anti-hunt prose rule at `## Deferred load points`. Move 2 (addressing unification) is explicitly scoped OUT of this cycle**, deferred pending its own spike per the entity's filed guidance above. Move 1 is the smallest-sufficient near-term step; Move 2 is held as the pre-registered escalation lever (see AC-1) if Move 1's measured live effect is insufficient — the same "hold the stronger mechanism until the cheaper one is measured" discipline sc5 applied to its boot-preamble retry.

**The single change.** Add one additive paragraph to `skills/first-officer/references/first-officer-shared-core.md`, at the end of the `## Deferred load points` section (after the five bullet-list load points, before `## Single-Entity Scope`). It does three things, symmetric to the existing zero-discovery no-hunt rule at Startup step 2: (a) name where a bare `references/…` load point resolves (the skill's own install directory, announced when the first-officer skill loaded), not the FO's cwd; (b) forbid a filesystem hunt for a contract/reference file known by name; (c) require STOP-and-report on an unresolved reference read instead of a search. The paragraph is written to cover every bare `references/…` read — so it also governs `references/fo-smallest-sufficient-mechanism.md` (named at line ~150, Working Principles) and the runtime-adapter reads (`references/claude-first-officer-runtime.md`, `references/claude-fo-dispatch.md`), not just the two `references/…` bullets in this section.

**Before/after wording** (template-text change, so exact wording per the stage-def rule):

BEFORE — the `## Deferred load points` bullet list ends at the `fo-dispatch-recovery` bullet, then the section ends; there is no addressing/anti-hunt rule for the `references/…` points.

AFTER — append this paragraph immediately after the `fo-dispatch-recovery` bullet:

> **A `references/…` load point resolves against this skill's own install directory — the base directory announced when the first-officer skill loaded — never against the FO's current working directory.** The `Skill(…)`-addressed points above resolve through the skill registry regardless of cwd; the bare `references/…` points do not, so a read issued from a working directory that is not the skill install dir (a worktree, a state checkout, a dispatched fixture root) can miss the file. If a `references/…` read does not resolve, STOP and report the unresolved path — do NOT broad-search the filesystem (`find` / `grep -r` / `ls -R` / recursive Glob/Grep) to hunt a contract or reference file you know by name. This is the reference-load twin of the zero-discovery no-hunt rule (Startup step 2): a filesystem sweep for a named contract file is the same fumble at a different trigger, and it is never the FO's next step.

**Why prose-only can move the needle here (and where its ceiling is).** The mechanism the fix leans on already exists and is already exercised on every FO session: the first-officer skill's install directory is *announced to the FO at skill load* (the same "Base directory for this skill: …" announcement that the `Skill(…)`-addressed load points resolve through, and that the FO's own *correct* production loads of these files already use). The find-hunt is the FO nondeterministically resolving the bare path against cwd instead of that announced base dir, then — finding nothing — searching. Part (a) re-anchors the resolution; parts (b)/(c) forbid the search fallback outright. The contract's own Working Principles warn that "a prose-only rule's ceiling is 'the wording is present'; wording-present is not behavior" — which is exactly why the load-bearing AC (AC-1) is a LIVE rate measurement, not a wording check, and why Move 2 (the structural, cwd-independent addressing fix) is pre-registered as the escalation lever if the live rate does not fall.

**No user-visible / CLI / docs-site surface changes.** The edit is to the FO's own shipped contract prose, which the FO reads at runtime; it is not CLI output, a command surface, a startup banner, host integration, or a docs-site page (confirmed: no docs-site file mirrors `## Deferred load points`; the only other hits are `.spacedock-state` entities and a `_proposals` note). No separate doc diff is required — the before/after contract wording above IS the change artifact, per the stage-def's "for template or skill text changes: specific before/after wording."
