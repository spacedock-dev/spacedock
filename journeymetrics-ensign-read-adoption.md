## Problem
The journeymetrics `--read` adoption metric (`status_read_calls`/`scoped_read_calls`, landed in hf) parses the FO front-door `spacedock claude -p` stream. But `status --read` adoption is principally an ENSIGN behavior — the contract sites that steer repeat-reads (and the site-6 hint hf trimmed) target the dispatched ensign, which runs as a separate team-agent session (`subagents/agent-*.jsonl`) whose transcript the metric does not parse. Empirically, four real FO front-door captures all register `status_read_calls=0`/`scoped_read_calls=0`. So the standing monitor does not observe the agent whose adoption it was built to measure, and hf's AC-7 before/after could only compare 0==0.

## What's needed
Extend the journeymetrics parse to fold the dispatched-ensign sub-agent transcript (`subagents/agent-*.jsonl` under the run's config dir) into the per-journey `--read` adoption counts, so the metric measures the ensign's `status --read` + scoped-`Read` behavior — the surface the contract sites and the trimmed site-6 hint actually steer. Then hf's adoption-not-regress check (pre-trim vs post-trim) becomes a meaningful before/after.

## Approach
The live harness (`internal/ensigncycle/journey_metrics_live_test.go:emitClaudeScenarioMetrics`) parses only `result.stream` (the FO front-door `claude -p` pipe) via `ParseClaudeJSONL`, then `BuildRecord`s a journey record. The ensign runs as a separate Claude Code sub-agent whose transcript lands on disk, never in `result.stream`.

The fold:
1. **Source** the dispatched-ensign transcripts for the journey. Reuse the proven discovery shape from `internal/claudeteam/contextbudget.go` (`scanSubagentMeta`): glob `{configDir}/projects/{encode(cwd)}/{FO-session-id}/subagents/agent-*.jsonl`. The live harness already controls HOME/config dir and knows the FO session id, so it can enumerate the journey's ensign transcripts.
2. **Parse** each transcript with the existing `ParseClaudeJSONL` — the on-disk `agent-*.jsonl` line shape is `{type:"assistant", message:{content:[{type:"tool_use", name, input}]}}`, identical to the front-door stream-json the parser already reads (extra on-disk top-level fields — `parentUuid`, `agentId`, … — are ignored by the `map[string]json.RawMessage` decode). Spike-confirmed below.
3. **Fold** by SUMMING each transcript's `StatusReadCalls`/`ScopedReadCalls` onto the FO observation's counters. Parse-per-transcript-then-sum (NOT concatenate-then-parse): tool-IDs are unique per session, so summing cannot cross-count, and the existing per-stream multi-delta toolID dedup stays correct within each transcript. Concatenating would risk toolID collision and conflate turn/token accounting across sessions.

Scope is the two `--read` adoption counters only (`status_read_calls`, `scoped_read_calls`). `turns`/`tokens`/`tool_calls` keep their FO-front-door semantics; broader cross-session aggregation is out of scope for this task.

Proposed surface: a folding entry point the live harness calls and a unit test drives directly with fixture bytes — e.g. `FoldEnsignReadAdoption(obs Observation, transcripts [][]byte) (Observation, error)`, returning `obs` with the two counters incremented by each transcript's parsed counts. The disk glob (step 1) lives in the live harness; the fixture unit test (AC-1) injects transcript bytes directly so the count-folding logic is exercised without a disk dependency.

## Spike result (riskiest mechanism — sourcing + folding the on-disk transcript)
Exercised end-to-end against a REAL dispatched-ensign transcript: `…/projects/-Users-clkao-git-spacedock-research-spacedock-v1/018c3c8d-…/subagents/agent-a28e0da724919e3e9.jsonl`. A throwaway in-package test fed the raw file to `ParseClaudeJSONL` (then deleted; not committed).

- **Sourcing/shape: SOUND.** The on-disk transcript parsed cleanly: `turns=76, tool_calls=85, scoped_read_calls=6`. The existing parser handles the on-disk shape with no change, and `readInputIsScoped` fires on real ensign scoped `Read`s (offset/limit present) — 6 detected. The fold's value on the scoped-Read axis is demonstrated on real data, not a fixture.
- **`status --read` detection on real data: GAP surfaced.** That same transcript carried 2 real `status --read` Bash tool_uses; the detector caught **0**. Both used `spacedock_launcher status --read …`. Sampling this project's ~482 `status --read` Bash tool_uses, the dominant launcher tokens immediately before `status --read` were: `spacedock_launcher` ×196, `./spacedock` ×38 (dev builds), `"$SPACEDOCK"` ×11 — all UNrecognized — vs `${SPACEDOCK_BIN:-spacedock}` ×24 + bare `spacedock` ×16 recognized by the current map. That breakdown categorizes 285 of the ~482 (a dominant-forms sample); the remaining ~197 are an uncategorized tail of mixed/edge forms. So the miss rate is a **range, ~86–92%** (40 of 285 categorized recognized → ~86% missed; ~40 of 482 corpus-wide → ~92% missed) — corpus-dependent, and excluding the `/tmp` dev-build `./spacedock` cohort shifts the figure but not the conclusion. The qualitative claim is robust: the vast majority of real launcher forms go unrecognized. Two distinct causes: (a) `commandInvokesStatusRead`'s allowlist `{spacedock, sd, ${SPACEDOCK_BIN:-spacedock}}` omits the `spacedock_launcher` shell function the dispatch fetch commands define and call (and the `./spacedock` dev build) — its comment claims it matches "the form the fetch commands emit," but real fetch commands wrap the launcher in that function; and (b) it keys on the exact unquoted `tokens[i-1]` with no quote-stripping, so the contract-canonical QUOTED `"${SPACEDOCK_BIN:-spacedock}"` form is dropped even though the contract prescribes it (shared-core:7). `"$SPACEDOCK"` is a legacy non-canonical variable, NOT the `SPACEDOCK_BIN` family the contract pins — so the widening targets the `SPACEDOCK_BIN` family (quoted-or-not) plus the dominant real launchers, not `$SPACEDOCK`.

Consequence: folding the transcript makes **scoped_read_calls** real on live data immediately, but **status_read_calls** stays vacuously ~0 on real data until the launcher recognition is widened — i.e. the fold alone does not by itself deliver the DoD's "real before/after instead of vacuous `0==0`" for the `status --read` half.

## Scope decision (resolved at the ideation gate, 2026-06-30)
The spike shows the fold (this task's committed mechanism) is sound, but on its own it only de-vacuums the scoped-Read half of the adoption number — the `status --read` half stays ~0 on real data until launcher recognition is widened. **Gate decision (index.md:44):** AC-2 — widening `commandInvokesStatusRead` — is confirmed IN scope for f5: same file (`internal/journeymetrics`), same parallel-safe wave, and it is what makes the `status --read` before/after non-vacuous on real data (the DoD's stated intent). The widening recognizes the real dominant launchers (`spacedock_launcher`, `./spacedock`, bare `spacedock`/`sd`) AND the contract-canonical `${SPACEDOCK_BIN:-spacedock}` family quoted-or-not — by NORMALIZING the launcher token (strip surrounding quotes; canonicalize the `SPACEDOCK_BIN` family), not by extending an exact-token allowlist. Staff review M10 corrected the earlier plan here: it named the wrong env var (`$SPACEDOCK`, where the contract invariant at shared-core:7 is `${SPACEDOCK_BIN:-spacedock}`) and the exact-token map could not recover the QUOTED `"${SPACEDOCK_BIN:-spacedock}"` form 82k's AC-1 depends on.

## Acceptance criteria
- **AC-1 (committed — the fold)** — A journey record's `status_read_calls`/`scoped_read_calls` include the dispatched-ensign sub-agent transcript's `status --read` Bash invocations and scoped `Read` calls, not just the FO front-door stream. Verified by a journeymetrics unit test over a fixture journey: an FO front-door stream with a known baseline (e.g. `status_read=0, scoped_read=1`) folded with an ensign transcript carrying one recognized-form `spacedock status --read` Bash call + one scoped `Read`, asserting the per-journey counts capture BOTH contributions (`status_read=1, scoped_read=2`), and equal the FO-only baseline when the ensign transcript carries neither (zero case). **Non-tautological by perturbation:** with the ensign-transcript fold removed, the counts drop to the FO-only value (`status_read=0, scoped_read=1`) and the assertion FAILS — the baseline can move the wrong way. (Real-data value for the scoped-Read axis is already evidenced by the spike: `scoped_read_calls=6` folded from a real ensign transcript.)
- **AC-2 (committed — gate-confirmed IN scope 2026-06-30, index.md:44; makes the `status --read` before/after non-vacuous)** — `status_read_calls` counts the real dominant invocation forms AND the contract-canonical launcher, not just an exact-token allowlist. Recognition NORMALIZES the launcher token immediately before `status` — strip surrounding quotes, then canonicalize the `SPACEDOCK_BIN` family (quoted-or-not) — before the membership test, so the canonical QUOTED `"${SPACEDOCK_BIN:-spacedock}"` form the contract prescribes (shared-core:7) is counted. The current `commandInvokesStatusRead` keys on exact `tokens[i-1]` with no quote-stripping and drops that quoted form — the form 82k's AC-1 depends on. Verified by extending the `TestCommandInvokesStatusRead` table with `spacedock_launcher status --read …`, `./spacedock status --read …`, and the contract-canonical quoted `"${SPACEDOCK_BIN:-spacedock}" status --read …` as positives, alongside the existing unquoted `${SPACEDOCK_BIN:-spacedock}` and bare positives, plus a negative that a launcher token alone — without a following `status --read` — does not match. Measured end-value: re-running the spike's real-transcript parse yields `status_read_calls > 0` (was 0). Note `$SPACEDOCK` is NOT a recognized form: it is a legacy variable, not the `SPACEDOCK_BIN` family the contract invariant pins.
