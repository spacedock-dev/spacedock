AC-6's shallow-boot measured-saving oracle (`internal/ensigncycle/shallow_boot_measure_test.go`, `assertShallowBootMeasured`) hard-fails CI on two absolute constants — `greetContextCeiling = 60000` and `teamRecacheSpikeFloor = 60000` — calibrated once against the pre-optimization ~160k/~89k baseline in task j9 (`0203-fo-efficiency`, shipped v0.20.3) and never revisited since. They no longer mean anything as a pass/fail gate. Replace them with recorded telemetry (turns-to-greet, greet-turn `cache_creation` tokens) that rides the existing `journeymetrics` ledger pipe, and close the per-PR visibility gap identified in the same conversation: the published `journey-costs-vX.json` ledger is release-cadence only and currently sourced from whichever manual `workflow_dispatch` run on `main` happened to run last (see `release.yml`'s `journey-ledger` job, `gh run list --branch main --limit 1`) — it never reflects the PR runs that already execute continuously (`runtime-live-e2e.yml` triggers on every PR into main once the live jobs' environment is approved) and already upload the exact raw stream needed (`live-artifacts/claude/<model>/claude-shared-scenarios/shallow-boot/claude-stream.jsonl`, ~90-day artifact retention).

## Problem

- The two AC-6 thresholds are magic numbers frozen against a baseline that predates most of the current contract; a red/green verdict against them carries no information about whether today's boot got better or worse.
- No historical trend exists for boot cost (turns, cache-creation tokens) at all — the release ledger is a single snapshot per cut, not a series.
- Per-PR live runs already produce the raw data needed but nothing reads or surfaces it; a regression introduced in a PR is invisible until (if ever) someone manually dispatches a main run before the next release.

## Proposed approach

Captain-agreed direction from conversation (ideation should firm up the specifics, not relitigate the shape):

1. **Record, don't gate.** In `runClaudeShallowBootScenario` (`claude_live_runner_test.go`), where `assertShallowBootMeasured` already computes the turn list and the greet-turn index, emit a `journeymetrics.Record` (via `journeymetrics.EmitRecord`, into the same `SPACEDOCK_JOURNEY_METRICS_DIR/shared-scenarios` dir the whole-run `shallow-boot` scenario record already uses) carrying `Turns: greet+1` and the greet turn's FULL `TokenTotals` (input, output, cache_read, and `cache_creation` — not `cache_creation` alone) as a distinct boot-window observation, so the pre-greet spike signal (currently the `teamRecacheSpikeFloor` check, which looks at `cache_creation` across the whole pre-greet window, not just the greet turn) isn't lost from the replacement telemetry; a future reader needs the full token shape to reconstruct both the ceiling and the spike story, not just one number. **Must use a distinct `ScenarioID` (e.g. `shallow-boot-window`), not `shallow-boot`.** `journeymetrics.recordFilename` (`internal/journeymetrics/record.go`) derives the on-disk filename from `ScenarioID--Runtime--Executor--Host--Mode--Model--MetricsState`; the whole-run record this scenario already publishes writes `shallow-boot--claude--llm--llm-live--<model>--measured.json` (confirmed by inspecting a real run's artifact bundle during ideation — see the backfill spike below), so reusing `shallow-boot` as the new observation's `ScenarioID` would silently overwrite that file instead of adding a sibling one.

   **Precise mechanics of the gate removal.** The two `t.Fatalf`s live in the CALLER (`runClaudeShallowBootScenario`); the actual threshold logic — the two branches that return `fmt.Errorf(...)` on ceiling/spike breach — lives inside `assertShallowBootMeasuredTurns` (`shallow_boot_measure_test.go`). Deleting only the caller's `t.Fatalf` and leaving `assertShallowBootMeasuredTurns` returning an error on breach just relocates the failure (the caller would need to ignore or downgrade the returned error instead). The two threshold branches must be removed (or loosened to a sanity-only tripwire) from `assertShallowBootMeasuredTurns` itself; only the structural "no assistant turns" error stays a hard failure. This directly breaks two EXISTING offline unit tests in `shallow_boot_measure_unit_test.go` that assert the current thresholds fire: `TestAssertShallowBootMeasuredOffline`'s negative-fixture case (asserts `eager-team-boot.stream.jsonl` — an ~89k pre-greet spike + over-ceiling greet — currently makes `assertShallowBootMeasured` return an error) and `TestShallowBootMeasureSignalsAreIndependent` (asserts both the ceiling-only and spike-only synthetic cases return errors). Implementation must update or retire these two tests in the same change, not leave them red or silently passing against a no-op check. Structural checks that are NOT threshold-based (`assertNoTeamCreateBeforeGreet`, `assertGreetInvokesNoDeferredFOSkill`) are unaffected and stay as hard gates.
2. **Widen release-ledger aggregation.** Change the `journey-ledger` job's discovery query in `release.yml` from "single latest `branch:main` run" to pulling journey-metrics from every successful Runtime Live E2E run (PR and main both) since the previous release tag, so the published ledger becomes a real aggregate/trend instead of one snapshot. Reuses artifacts that already exist; no new upload plumbing needed.

   **Fix the flat-copy collision this widening would otherwise hit.** `release.yml`'s existing download step (`Download latest journey metrics artifacts`) flat-copies every downloaded run's `journey-metrics/*.json` into ONE directory: `find "$RUNNER_TEMP/runtime-live-artifacts" -path '*/journey-metrics/*.json' -type f -exec cp {} "$RUNNER_TEMP/journey-metrics/" \;`. `journeymetrics.recordFilename` has no run-distinguishing component, so once discovery widens from 1 run to N, every run's `<scenario>--<runtime>--...--<state>.json` for the same scenario/model collides on the SAME filename in that one flat directory — each `cp` silently overwrites the previous run's file, and the aggregation collapses back to exactly one observation per scenario/model regardless of how many runs were discovered. This is the same overwrite hazard step 1 already caught and fixed on the emission side (`shallow-boot` vs `shallow-boot-window`), missed here on the aggregation side. **Fix:** download each discovered run into its OWN subdirectory (e.g. `$RUNNER_TEMP/journey-metrics/<run-id>/`) and copy that run's files there instead of flattening into a single directory. `journeymetrics.ReadRecordsDir` already walks the metrics dir recursively (`filepath.WalkDir`), so it needs no Go-side change — only the shell copy step changes.

   **Add run provenance to the `Record` schema.** `journeymetrics.Record` (`internal/journeymetrics/types.go`) currently has no field identifying which run/commit/time produced it — `Source` is a static string, not per-run. Once a scenario/model can hold N observations, AC-2's own "traceable to more than one run" claim and AC-3's delta baseline (below) both need a way to tell observations apart and order them by recency. Add three optional fields to `Record` (threaded through `recordJSON` and the custom `MarshalJSON`, all `omitempty`): `RunID string` (json `run_id`, populated from `$GITHUB_RUN_ID`), `RunURL string` (json `run_url`, built from `$GITHUB_SERVER_URL`/`$GITHUB_REPOSITORY`/`$GITHUB_RUN_ID`), and `CapturedAt string` (json `captured_at`, an RFC3339 timestamp set at emission time). These are populate-if-present fields — a record emitted outside CI (a local test run) simply omits them — so no existing fixture or golden file needs updating for records that don't set them. `ScenarioLedgerEntry.Observations` (`ledger.go`) needs no shape change; `AggregateLedger`'s existing per-scenario grouping already produces the right container, it just starts holding richer entries.

   **Pin the aggregation window.** "Since the previous release tag" means since the immediately-prior tag OF ANY KIND (stable or `-pre`) — a strictly incremental window, so a `-pre` release's ledger does not re-include runs already folded into an earlier `-pre` in the same cycle. Every successful Runtime Live E2E run in that window counts, regardless of whether its triggering PR was later merged, closed unmerged, or is still open — the observation is about boot behavior on that commit at that time, not about the PR's eventual fate, and gating on merge state would require an additional GitHub API call per PR that the discovery step does not currently make.
3. **Per-PR delta comment.** Add a step (triggered from a PR's own live run, once it completes) that reads the previously *published* release's `journey-costs-vX.json` (the last `gh release` asset, e.g. via the same `gh api` release-asset lookup used in this conversation), computes a delta per scenario/model against the current PR run's freshly emitted records, and posts it as a single updating PR comment (not a new comment per push). Scope this to whatever the ledger already tracks generically (turns, tokens, cost) rather than one-off special-casing the boot-window metric — the diff mechanism doesn't care which scenario it's comparing.

   **Delta baseline over multi-observation ledgers.** Once step 2 ships, a published ledger holds N observations per scenario/model, not one — "(PR value − published value)" is ambiguous until a baseline reduction is picked. Baseline = the single observation with the LATEST `captured_at` timestamp for the matching scenario/model (the run-provenance field step 2 adds), not a mean or max — the comment is answering "did this PR move boot cost relative to where it stood most recently," not summarizing the whole trend, and "latest" needs no new aggregation logic beyond a sort the provenance field already enables. The comment names the specific compared run (via `RunURL`) so the baseline is auditable, not just a bare number.

   **Job permissions.** The workflow-level `permissions: contents: read` in `runtime-live-e2e.yml` does not grant comment-posting; the job that runs this new step needs its own `permissions: pull-requests: write` block (GitHub Actions job-level permissions can grant beyond the workflow default).
4. **Retroactively backfill already-published release ledgers.** Once AC-1's extraction logic exists (turns-to-greet + greet-turn `CacheCreation` from a raw `claude-stream.jsonl`), apply that SAME logic to the ALREADY-PUBLISHED `journey-costs-vX.json` release assets, not just future releases. For each release identified as recoverable (see AC-4): **first download and archive the release's CURRENT `journey-costs-vX.json` asset as a local backup** (`gh release download <tag> -p journey-costs-v<version>.json -O <backup-path>`) before touching anything, since `gh release upload --clobber` is a destructive overwrite of a public artifact with no undo; then download that release's source Runtime Live E2E run's artifacts (`gh run download <run-id>`), extract `live-artifacts/claude/<model>/claude-shared-scenarios/shallow-boot/claude-stream.jsonl`, compute the new `shallow-boot-window` observation from it (the same extraction logic AC-1 adds, run standalone against archived data rather than at live-test time), add it to that source run's metrics dir alongside the already-recovered records, rebuild the ledger (`go run ./cmd/spacedock-release journey-costs <version> --metrics-dir <dir> --out journey-costs-v<version>.json` — the existing command, unmodified), diff the rebuilt ledger's `scenarios` array against the backed-up original to confirm the ONLY change is the added `shallow-boot-window` entry (rebuilding re-normalizes every record — `normalizeRecord` restamps `SchemaVersion` and recomputes token totals, `record.go:107`/`ledger.go:49` — so a rebuild quirk could otherwise silently mutate historical data that has nothing to do with this backfill), and only then republish (`gh release upload <tag> journey-costs-v<version>.json --clobber` — the same command `release.yml`'s `journey-ledger` job already uses). If the diff shows any change beyond the addition, STOP and do not upload — restore from the backup and investigate. Releases identified as NOT recoverable are left unmodified.

   **Backfill traceability spike (performed during ideation, 2026-07-02, against the real repo and real archived streams — not simulated).** The riskiest unverified mechanism — whether each already-published release from v0.20.3 through v0.24.0-pre1 can still be traced to the live-e2e run/artifacts that fed it, and whether those artifacts still contain what the backfill needs — was exercised end-to-end. Findings:

   - **Reconstructing "which run fed which release" is possible without a captured log, and the reconstruction was independently confirmed, not just inferred.** `release.yml`'s `journey-ledger` job picks "the latest successful `Runtime Live E2E` run on `branch:main`" at cut time but never records which run id it picked. Ideation reconstructed the mapping by correlating each release's publish timestamp (`gh release list`) against the full history of successful main-branch `Runtime Live E2E` runs (`gh run list --workflow "Runtime Live E2E" --branch main --status success --json databaseId,createdAt`; 10 such runs exist total) and taking, for each release, the latest run created before it. This reconstruction was then confirmed independently by diffing the already-published `journey-costs-vX.json` scenario payloads pairwise: `v0.20.3`, `v0.20.4`, `v0.22.0`, `v0.23.0-pre.1`, `v0.23.0-pre.2`, and `v0.23.0-pre.3` are all byte-identical in their `scenarios` array (proving they share one source run — no new main-branch live run landed between 2026-06-13 and 2026-06-22), and `v0.23.0` / `v0.24.0-pre1` are byte-identical to each other (a second shared-source group). This byte-identity is ground truth independent of the timestamp-correlation guess, and it matched the guess exactly for both groups.
   - **Artifact retention is NOT the limiting factor for any release in scope.** `gh api repos/spacedock-dev/spacedock/actions/runs/<id>/artifacts` was checked for all 10 successful main-branch runs (oldest: 2026-04-16). None are expired as of today (2026-07-02); the oldest expire ~2026-07-15, and every run that actually feeds a v0.20.3-v0.24.0-pre1 release expires no earlier than ~2026-09-11.
   - **The real limiter: the source run's commit is too old, not its artifacts.** The `shallow-boot` shared scenario (and the whole AC-6 boot-window assertion) was introduced in PR #365 (`fe4261be`, landed 2026-06-14T05:10:07Z). The June-13 run that feeds the `v0.20.3`/`v0.20.4`/`v0.22.0`/`v0.23.0-pre.1..3` group (run `27479907054`, commit `79284ca8`, 2026-06-13T21:26:14Z) predates that PR — `git show 79284ca8:internal/ensigncycle/shallow_boot_measure_test.go` fails (file absent at that commit), and the downloaded artifact bundle for that run has only 5 of the 6 shared-scenario directories (no `shallow-boot`). The `shallow-boot` scenario simply never ran in that source run, so there is no raw stream to extract a boot-window observation from — this is not a retention or traceability gap, the observation was never produced. The `v0.23.0-pre.4` source run (`27931963802`, commit `6ea56f95`) and the `v0.23.0`/`v0.24.0-pre1` source run (`28432388663`, commit `e3f85ec3`) both postdate PR #365 and DO carry a `shallow-boot/claude-stream.jsonl`.
   - **The extraction mechanism itself was proven against the two recoverable runs' real archived streams** (a throwaway Go test against `internal/journeymetrics.ParseClaudeTurns`, run once during ideation and then discarded, per the spike-first policy — not committed): `run 27931963802` (feeds `v0.23.0-pre.4`) yields turnsToGreet=18, greetCacheCreation=1562, greetContext=38225; `run 28432388663` (feeds `v0.23.0`/`v0.24.0-pre1`) yields turnsToGreet=20, greetCacheCreation=1576, greetContext=39120 — both comfortably below the 60k thresholds AC-6 currently hard-fails on, consistent with the problem statement that the constants no longer carry information.
   - **The "6 of 9 unrecoverable" result is a policy choice, not a forced outcome — recorded here for the captain to ratify knowingly.** All 6 non-recoverable releases (`v0.20.3`, `v0.20.4`, `v0.22.0`, `v0.23.0-pre.1`, `v0.23.0-pre.2`, `v0.23.0-pre.3`) were themselves CUT AFTER PR #365 (the `shallow-boot` scenario) landed — only their SPECIFIC shared source run (the one "latest main success" happened to resolve to at each cut) predates it. `runtime-live-e2e.yml` runs on every PR into `main`, so same-window PR-triggered runs that DO carry a `shallow-boot` stream plausibly exist within the ~90-day retention for all 6 — "unrecoverable" here means "not traceable to THAT release's own specific source run," not "no shallow-boot data exists anywhere in the window."
     - **Recommended default (what this ideation proposes): fidelity over completeness.** Only backfill from the exact run that fed the rest of that release's ledger. Splicing in a different PR run's stream would mean one release's ledger has 5 scenarios sourced from run X and a 6th spliced from unrelated run Y — internally inconsistent provenance within a single release, for a gain of at most 6 more `shallow-boot-window` data points that were never really part of that release's own measured moment.
     - **Alternative (rejected by default, but real): splice a same-window PR run's `shallow-boot` stream in for all 9.** This would achieve full backfill coverage at the cost of that internal-consistency guarantee, and would need its own traceability spike (confirming a same-window PR run's artifacts are still downloadable) before being treated as verified.
     - This ideation recommends the fidelity default and asks the captain to ratify it explicitly at the gate, rather than presenting "3 of 9" as if no other option existed.

5. **Follow-up round (captain-directed, 2026-07-03, after a detached fable review of the in-flight implementation): richer boot-window provenance, plus fixes the review found.** PR #470 was not yet merged, so this round lands on the same branch/worktree rather than a new task.

   **Boot-window record gains three more fields.** `BuildShallowBootWindowRecord`'s `journeymetrics.Record` (and the shared `Observation`/`Record` types) gain: `BaselineTokens` (the FIRST turn's full `TokenTotals` — a reference point for how the boot started; per-turn usage is NOT cumulative across turns, so only `Tokens.Context() - BaselineTokens.Context()` is a defensible derived quantity, not a full-struct subtraction), `PreGreetPeakCacheCreation` (the MAXIMUM `cache_creation` across every turn strictly before the greet turn — the exact aggregate the removed `teamRecacheSpikeFloor` check compared against its floor; `BaselineTokens` alone does NOT reconstruct this for a multi-turn pre-greet window, since the spike can land on any pre-greet turn, not just the first), `ClaudeCodeVersion` (the stream's `system`/`init` event's `claude_code_version` field, via a new `journeymetrics.ParseClaudeCodeVersion`), and `ResolvedModel` (the same `init` event's `model` field, via `journeymetrics.ParseClaudeInitModel` — confirmed against REAL CI-captured fixtures, e.g. `internal/ensigncycle/testdata/sonnet_teamdelete_*.stream.jsonl`, that the "sonnet" CI-matrix alias resolves to `claude-sonnet-4-6` in the raw stream, more precise than the alias recorded in `Model`). All four are additive, `omitempty` fields on the existing optional-field pattern (`RunID`/`RunURL`/`CapturedAt` precedent) — no existing fixture needs updating.

   **C1 fix (production bug the review caught in the ALREADY-SHIPPED AC-3 job, not new scope):** `runtime-live-e2e.yml`'s `journey-delta-comment` job hardcoded `--metrics-dir` to `"$RUNNER_TEMP/current-run-artifacts/live-artifacts/journey-metrics"`, but a real run's `download-artifact` output nests the journey-metrics JSON several directories deeper (verified against run 28432388663's zip) — the hardcoded path is empty, so `journeymetrics.ReadRecordsDir` errors and REDs the job under `set -euo pipefail` on every PR. Fixed with a new "Locate this run's journey metrics" step using `release.yml`'s own layout-agnostic `find -path '*/journey-metrics/*.json' -exec cp` pattern (`ReadRecordsDir`'s recursive walk needs no Go-side change).

   **TRIM (captain-ordered de-scope of AC-4's shipped tooling, ~530 lines).** The AC-4 backfill's two CLI subcommands (`shallow-boot-window-record`, `ledger-diff`) and `internal/release`'s `ledgerdiff.go` package + tests are REMOVED. The backfill is a captain-flagged, one-time manual procedure — shipping permanent CLI surface for it was scope the review judged unnecessary. Replaced by a documented runbook: extraction reuses the exported `ensigncycle.BuildShallowBootWindowRecord` via a throwaway (uncommitted) `go run` script against each archived stream, and the pre-upload structural safeguard is `jq -S .scenarios <original> | diff - <(jq -S .scenarios <rebuilt>)` — any diff output means STOP, do not upload. AC-4's Verified-by is unchanged in substance (backup, diff, then publish) but no longer names a shipped CLI.

   **PR delta comment Minors.** The comment now shows `cache_read`/`cache_creation` deltas as separate columns (not just the token total — they differ ~12× in cost and meaning for a boot metric); a scenario/model with no matching baseline renders `n/a (new)` in its delta cells instead of a self-delta against an implicit zero baseline (which read as a huge, meaningless "increase"); and the sticky comment is now found by its `<!-- spacedock:journey-delta -->` marker and updated by id (`gh api .../issues/comments/<id> -X PATCH`) instead of `gh pr comment --edit-last`, which targets "the poster's last comment on the PR" and could silently edit the wrong comment if another automated comment interleaves.

   **Open question for the captain, not resolved now:** the 3 already-backfilled releases (`v0.23.0-pre.4`, `v0.23.0`, `v0.24.0-pre1`) were backfilled with the PRE-this-round `shallow-boot-window` shape and are missing `BaselineTokens`/`PreGreetPeakCacheCreation`/`ClaudeCodeVersion`/`ResolvedModel`. Whether to re-run the backfill runbook against them to add the new fields (a second one-time manual procedure) is left for the captain to decide once this round ships — not executed as part of this round.

## Out of scope

- A live/real-time dashboard beyond the PR comment.
- Expanding tracked scenarios beyond the current six. **Clarification:** `shallow-boot-window` is a second `scenario_id` in the ledger, but it is NOT a new tracked scenario in the sense this bullet means — no new live-harness scenario/fixture/prompt is added; `shallow-boot-window` is a second OBSERVATION emitted from the EXISTING `shallow-boot` scenario run (same live test, same fixture, same prompt), just carrying the boot-window slice of that run's data under its own `scenario_id` so it doesn't collide with the whole-run record. The six live-harness scenarios (`gate-guardrail`, `rejection-flow`, `feedback-3-cycle-escalation`, `merge-hook-guardrail`, `filing`, `shallow-boot`) stay six; the ledger's `scenario_id` count in `journey-costs-vX.json` goes to seven entries once `shallow-boot-window` starts publishing.

## Acceptance criteria

**AC-1 - The shallow-boot live scenario no longer fails CI on the absolute 60k/60k constants; turns-to-greet and the greet turn's full token usage are recorded as a `shallow-boot-window` journeymetrics observation instead.**
Verified by: an offline fixture unit test (mirroring `shallow_boot_measure_unit_test.go`'s pattern, table-driven over synthetic `ClaudeTurn` slices) asserting `EmitRecord` writes `shallow-boot-window--claude--llm--llm-live--<model>--measured.json` — a file DISTINCT from the pre-existing `shallow-boot--...--measured.json` (both present after one scenario run, neither overwriting the other) — carrying `Turns == greetIndex+1` and `Tokens` equal to the greet turn's full actual `TokenTotals` (input, output, cache_read, cache_creation) from the fixture stream, not `CacheCreation` alone. A second assertion proves the hard gate is gone at its actual location, `assertShallowBootMeasuredTurns`'s two threshold branches (NOT merely the caller's `t.Fatalf` in `runClaudeShallowBootScenario`): feeding it the existing `eager-team-boot.stream.jsonl` fixture (the ~89k pre-greet spike + over-ceiling greet) no longer returns an error. This requires updating the two existing offline tests that currently assert the opposite — `TestAssertShallowBootMeasuredOffline`'s negative-fixture case and `TestShallowBootMeasureSignalsAreIndependent` — in the same change; AC-1 is not met if those are left asserting the removed thresholds (whether still red, or silently no-op-passing). Independent of prose: all checks read emitted JSON / function return values, not a description of the change.

**AC-2 - The published release ledger reflects PR-run history, not a single manual main dispatch, with each observation traceable to the specific run that produced it.**
Verified by two checks, both required (the first proves the widening isn't silently defeated, the second proves the traceability the AC text itself claims):
(a) a fixture/mock test for `journeymetrics.AggregateLedger`, exercised via `go run ./cmd/spacedock-release journey-costs` against a `--metrics-dir` populated the way the fixed `release.yml` step now populates it — MULTIPLE per-run SUBDIRECTORIES (not one flat directory) built from copies of the real per-run metrics dirs recovered during the ideation spike, from two distinct source runs — asserting the resulting `journey-costs-vX.json`'s `summary.observation_count` for a given scenario is greater than 1, against the independent baseline of today's single-run behavior (`observation_count` per scenario == 1). A regression test pinning the OLD flat-copy shape (all runs' files copied into one directory) still collapses to 1 observation confirms the fix is what closes the gap, not an incidental side effect.
(b) the same fixture ledger's observations for that scenario carry distinct, non-empty `run_id`/`run_url` values matching the two distinct source runs used to build the fixture — proving "traceable to more than one run" against actual provenance data, not just a count.

**AC-3 - A PR gets a visible delta of its own live-run numbers against the LATEST-by-`captured_at` observation in the previously published release ledger, for each scenario/model.**
Verified by: a fixture test driving the new delta step with (a) a stub previous-release ledger (a `journey-costs-vX.json` fixture) containing MULTIPLE observations per scenario/model with distinct `captured_at` timestamps (exercising the multi-observation shape AC-2 produces, not a single-observation stand-in) and (b) a fixture PR-run metrics set with deliberately different turns/tokens per scenario, asserting the rendered comment body's per-scenario delta equals `(PR value − the ledger observation with the latest captured_at for that scenario/model)` exactly — a second fixture case where the observations are deliberately given out-of-order `captured_at` values (not sorted by array position) proves the selection is by timestamp, not "last in the array." A second run of the same step against an updated PR-run fixture asserts the SAME comment id/marker is reused (an update, not a second comment) — verified against a stubbed `gh pr comment` invocation's args, not a live GitHub call.

**AC-4 - Every already-published release whose source live-e2e run still carries a `shallow-boot` execution has its `journey-costs-vX.json` republished with the new `shallow-boot-window` observation ADDED and every pre-existing entry PRESERVED UNCHANGED; releases whose source run predates the scenario are named and left unmodified (see the ratified provenance-fidelity policy in Proposed approach step 4).**
Verified by, for each of the 3 recoverable releases (`v0.23.0-pre.4`, `v0.23.0`, `v0.24.0-pre1`):
(a) before republishing, the ORIGINAL `journey-costs-v<version>.json` is downloaded and archived as a local backup (the step 4 safeguard) — its `scenarios` array is the pre-image every later check compares against;
