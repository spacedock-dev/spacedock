AC-6's shallow-boot measured-saving oracle (`internal/ensigncycle/shallow_boot_measure_test.go`, `assertShallowBootMeasured`) hard-fails CI on two absolute constants — `greetContextCeiling = 60000` and `teamRecacheSpikeFloor = 60000` — calibrated once against the pre-optimization ~160k/~89k baseline in task j9 (`0203-fo-efficiency`, shipped v0.20.3) and never revisited since. They no longer mean anything as a pass/fail gate. Replace them with recorded telemetry (turns-to-greet, greet-turn `cache_creation` tokens) that rides the existing `journeymetrics` ledger pipe, and close the per-PR visibility gap identified in the same conversation: the published `journey-costs-vX.json` ledger is release-cadence only and currently sourced from whichever manual `workflow_dispatch` run on `main` happened to run last (see `release.yml`'s `journey-ledger` job, `gh run list --branch main --limit 1`) — it never reflects the PR runs that already execute continuously (`runtime-live-e2e.yml` triggers on every PR into main once the live jobs' environment is approved) and already upload the exact raw stream needed (`live-artifacts/claude/<model>/claude-shared-scenarios/shallow-boot/claude-stream.jsonl`, ~90-day artifact retention).

## Problem

- The two AC-6 thresholds are magic numbers frozen against a baseline that predates most of the current contract; a red/green verdict against them carries no information about whether today's boot got better or worse.
- No historical trend exists for boot cost (turns, cache-creation tokens) at all — the release ledger is a single snapshot per cut, not a series.
- Per-PR live runs already produce the raw data needed but nothing reads or surfaces it; a regression introduced in a PR is invisible until (if ever) someone manually dispatches a main run before the next release.

## Proposed approach

Captain-agreed direction from conversation (ideation should firm up the specifics, not relitigate the shape):

1. **Record, don't gate.** In `runClaudeShallowBootScenario` (`claude_live_runner_test.go`), where `assertShallowBootMeasured` already computes the turn list and the greet-turn index, emit a `journeymetrics.Record` (via `journeymetrics.EmitRecord`, into the same `SPACEDOCK_JOURNEY_METRICS_DIR/shared-scenarios` dir the whole-run `shallow-boot` scenario record already uses) carrying `Turns: greet+1` and the greet turn's `TokenTotals` (specifically `CacheCreation`) as a distinct boot-window observation. **Must use a distinct `ScenarioID` (e.g. `shallow-boot-window`), not `shallow-boot`.** `journeymetrics.recordFilename` (`internal/journeymetrics/record.go`) derives the on-disk filename from `ScenarioID--Runtime--Executor--Host--Mode--Model--MetricsState`; the whole-run record this scenario already publishes writes `shallow-boot--claude--llm--llm-live--<model>--measured.json` (confirmed by inspecting a real run's artifact bundle during ideation — see the backfill spike below), so reusing `shallow-boot` as the new observation's `ScenarioID` would silently overwrite that file instead of adding a sibling one. Drop (or drastically loosen to a sanity-only tripwire, not the current tight absolute number) the two `t.Fatalf`s. Structural checks that are NOT threshold-based (`assertNoTeamCreateBeforeGreet`, `assertGreetInvokesNoDeferredFOSkill`) are unaffected and stay as hard gates.
2. **Widen release-ledger aggregation.** Change the `journey-ledger` job's discovery query in `release.yml` from "single latest `branch:main` run" to pulling journey-metrics from every successful Runtime Live E2E run (PR and main both) since the previous release tag, so the published ledger becomes a real aggregate/trend instead of one snapshot. Reuses artifacts that already exist; no new upload plumbing needed.
3. **Per-PR delta comment.** Add a step (triggered from a PR's own live run, once it completes) that reads the previously *published* release's `journey-costs-vX.json` (the last `gh release` asset, e.g. via the same `gh api` release-asset lookup used in this conversation), computes a delta per scenario/model against the current PR run's freshly emitted records, and posts it as a single updating PR comment (not a new comment per push). Scope this to whatever the ledger already tracks generically (turns, tokens, cost) rather than one-off special-casing the boot-window metric — the diff mechanism doesn't care which scenario it's comparing.
4. **Retroactively backfill already-published release ledgers.** Once AC-1's extraction logic exists (turns-to-greet + greet-turn `CacheCreation` from a raw `claude-stream.jsonl`), apply that SAME logic to the ALREADY-PUBLISHED `journey-costs-vX.json` release assets, not just future releases. For each release identified as recoverable (see AC-4): download that release's source Runtime Live E2E run's artifacts (`gh run download <run-id>`), extract `live-artifacts/claude/<model>/claude-shared-scenarios/shallow-boot/claude-stream.jsonl`, compute the new `shallow-boot-window` observation from it (the same extraction logic AC-1 adds, run standalone against archived data rather than at live-test time), add it to that source run's metrics dir alongside the already-recovered records, rebuild the ledger (`go run ./cmd/spacedock-release journey-costs <version> --metrics-dir <dir> --out journey-costs-v<version>.json` — the existing command, unmodified), and republish (`gh release upload <tag> journey-costs-v<version>.json --clobber` — the same command `release.yml`'s `journey-ledger` job already uses). Releases identified as NOT recoverable are left unmodified.

   **Backfill traceability spike (performed during ideation, 2026-07-02, against the real repo and real archived streams — not simulated).** The riskiest unverified mechanism — whether each already-published release from v0.20.3 through v0.24.0-pre1 can still be traced to the live-e2e run/artifacts that fed it, and whether those artifacts still contain what the backfill needs — was exercised end-to-end. Findings:

   - **Reconstructing "which run fed which release" is possible without a captured log, and the reconstruction was independently confirmed, not just inferred.** `release.yml`'s `journey-ledger` job picks "the latest successful `Runtime Live E2E` run on `branch:main`" at cut time but never records which run id it picked. Ideation reconstructed the mapping by correlating each release's publish timestamp (`gh release list`) against the full history of successful main-branch `Runtime Live E2E` runs (`gh run list --workflow "Runtime Live E2E" --branch main --status success --json databaseId,createdAt`; 10 such runs exist total) and taking, for each release, the latest run created before it. This reconstruction was then confirmed independently by diffing the already-published `journey-costs-vX.json` scenario payloads pairwise: `v0.20.3`, `v0.20.4`, `v0.22.0`, `v0.23.0-pre.1`, `v0.23.0-pre.2`, and `v0.23.0-pre.3` are all byte-identical in their `scenarios` array (proving they share one source run — no new main-branch live run landed between 2026-06-13 and 2026-06-22), and `v0.23.0` / `v0.24.0-pre1` are byte-identical to each other (a second shared-source group). This byte-identity is ground truth independent of the timestamp-correlation guess, and it matched the guess exactly for both groups.
   - **Artifact retention is NOT the limiting factor for any release in scope.** `gh api repos/spacedock-dev/spacedock/actions/runs/<id>/artifacts` was checked for all 10 successful main-branch runs (oldest: 2026-04-16). None are expired as of today (2026-07-02); the oldest expire ~2026-07-15, and every run that actually feeds a v0.20.3-v0.24.0-pre1 release expires no earlier than ~2026-09-11.
   - **The real limiter: the source run's commit is too old, not its artifacts.** The `shallow-boot` shared scenario (and the whole AC-6 boot-window assertion) was introduced in PR #365 (`fe4261be`, landed 2026-06-14T05:10:07Z). The June-13 run that feeds the `v0.20.3`/`v0.20.4`/`v0.22.0`/`v0.23.0-pre.1..3` group (run `27479907054`, commit `79284ca8`, 2026-06-13T21:26:14Z) predates that PR — `git show 79284ca8:internal/ensigncycle/shallow_boot_measure_test.go` fails (file absent at that commit), and the downloaded artifact bundle for that run has only 5 of the 6 shared-scenario directories (no `shallow-boot`). The `shallow-boot` scenario simply never ran in that source run, so there is no raw stream to extract a boot-window observation from — this is not a retention or traceability gap, the observation was never produced. The `v0.23.0-pre.4` source run (`27931963802`, commit `6ea56f95`) and the `v0.23.0`/`v0.24.0-pre1` source run (`28432388663`, commit `e3f85ec3`) both postdate PR #365 and DO carry a `shallow-boot/claude-stream.jsonl`.
   - **The extraction mechanism itself was proven against the two recoverable runs' real archived streams** (a throwaway Go test against `internal/journeymetrics.ParseClaudeTurns`, run once during ideation and then discarded, per the spike-first policy — not committed): `run 27931963802` (feeds `v0.23.0-pre.4`) yields turnsToGreet=18, greetCacheCreation=1562, greetContext=38225; `run 28432388663` (feeds `v0.23.0`/`v0.24.0-pre1`) yields turnsToGreet=20, greetCacheCreation=1576, greetContext=39120 — both comfortably below the 60k thresholds AC-6 currently hard-fails on, consistent with the problem statement that the constants no longer carry information.
   - **Determination: of the 9 named releases, 3 are backfillable (`v0.23.0-pre.4`, `v0.23.0`, `v0.24.0-pre1`); 6 are NOT (`v0.20.3`, `v0.20.4`, `v0.22.0`, `v0.23.0-pre.1`, `v0.23.0-pre.2`, `v0.23.0-pre.3`) because their shared source run predates the scenario under measurement, not because anything expired.** Recorded here rather than silently skipped, per the ideation stage's spike-first requirement.

Independent of prose: both checks read emitted JSON / test exit status, not a description of the change.

**AC-2 - The published release ledger reflects PR-run history, not a single manual main dispatch.**
Verified by: a fixture/mock test for `journeymetrics.AggregateLedger` (or the widened `journey-ledger` discovery query, exercised via `go run ./cmd/spacedock-release journey-costs` against a `--metrics-dir` populated from a MULTI-run fixture set — e.g. copies of the real per-run metrics dirs recovered during the ideation spike, from two distinct source runs) asserting the resulting `journey-costs-vX.json`'s `summary.observation_count` for a given scenario is greater than 1 and traceable to more than one run, against the independent baseline of today's single-run behavior (`observation_count` per scenario == 1, one snapshot). **AC-3 - A PR gets a visible delta of its own live-run numbers against the previously published release ledger.**
Verified by: a fixture test driving the new delta step with (a) a stub previous-release ledger (a `journey-costs-vX.json` fixture, e.g. the real `v0.23.0` asset downloaded during ideation) and (b) a fixture PR-run metrics set with deliberately different turns/tokens per scenario, asserting the rendered comment body's per-scenario delta values equal `(PR value - published value)` exactly, and a second run of the same step against an updated PR-run fixture asserts the SAME comment id/marker is reused (an update, not a second comment) — verified against a stubbed `gh pr comment` invocation's args, not a live GitHub call.

**AC-4 - Every already-published release whose source live-e2e run still carries a `shallow-boot` execution has its `journey-costs-vX.json` republished with the new `shallow-boot-window` observation added; releases whose source run predates the scenario are named and left unmodified.**
Verified by: reproducing the ideation-stage backfill spike's determination as an implementation-time check — for each of the 3 recoverable releases (`v0.23.0-pre.4`, `v0.23.0`, `v0.24.0-pre1`), after republishing, `gh release view <tag> --json assets` still lists exactly one `journey-costs-v<version>.json` asset, and downloading it (`gh release download <tag> -p journey-costs-v<version>.json`) shows a `shallow-boot-window` entry under `scenarios` with `Turns`/`Tokens.CacheCreation` matching the values independently computed by the ideation spike (turnsToGreet=18/greetCacheCreation=1562 for `v0.23.0-pre.4`; turnsToGreet=20/greetCacheCreation=1576 for `v0.23.0`/`v0.24.0-pre1`) — an external check against the actual GitHub Release asset, not local file state. ### Summary
