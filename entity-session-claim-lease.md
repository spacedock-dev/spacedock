Give each entity a durable claim naming the session allowed to mutate it, so two driving First Officers sharing one state checkout cannot select, dispatch, or mutate the same entity.

## Problem

`docs/dev/README.md:47` declares that while a sprint is actively driven, other FO sessions sharing the state checkout "stay out of its members", and that ownership is coordinated out-of-band "until a sprint carries a machine-readable owner". It names `xp` as the graduation trigger, but `xp` is scoped to an FO-Commander message transport and carries no notion of mutation authority, acquisition, or takeover — so no task currently owns the guarantee, and `xp` is unscored.

The advisory form is demonstrably insufficient. On 2026-07-25 a second FO booted into this workflow while the Commander was actively driving, found `state ready` blocked by an uncommitted stage report, and committed and pushed sprint member `first-officer-gate-command-lifecycle`'s in-flight cycle-34 report. The rule existed and was unambiguous; nothing in the boot path surfaced either the rule or the live peer. `status --boot` reported `team_state` for the booting session's own team and a local `pr:` mirror; neither indicates that another session holds the entity. Peer commits landed on the state branch minutes after the intrusion, confirming the owner was live throughout.

Two adjacent tasks touch the area without covering it: `sy` defines captain-authorized active scope within one session, and `mzk` asks for ownership tracing before acting on shared GitHub state. Neither supplies a durable, machine-checked owner for an entity.

## Proposed approach

Ideation owns the design. These are captain rulings from the 2026-07-25 shaping conversation and bind it:

- The claim is keyed to the **entity and session**, not the sprint. A sprint is a query whose membership is generated by its own review rounds — all five current durable-decisions members were filed mid-sprint — so a sprint-keyed claim leaves membership undefined exactly when the sprint is most active. A newly filed entity is unclaimed until claimed.
- Workstream or sprint selection is a **policy layered over the primitive**, not a second primitive. Claiming everything matching a status query is a loop over per-entity acquisition. Auto-claiming successors a review round spawns is captain-authorized, never silent.
- Enforcement starts at **two points**: boot surfaces the claim, and the state-mutation seam refuses a non-owner. Additional guard points are added only when one of these proves insufficient — a new standing enforcement process is the last resort under the working principles.
- Expiry **marks a claim stale and never auto-steals**. Takeover is captain-authorized and per entity.
- Acquisition should ride the existing state publisher rather than introduce a second writer. A git-backed shared checkout already provides compare-and-swap: acquisition is a fast-forward-only commit, and a conflicting acquirer loses the push and re-reads to name the current owner. Note `sync-merge-guard-archive-state` is concurrently building `internal/statesync` with exactly non-fast-forward detection and re-push.
- Owner identity already exists per host and is already read by the binary: `dispatch reconcile` matches `leadSessionId` against `$CLAUDE_CODE_SESSION_ID`; Codex exposes `CODEX_THREAD_ID` and Pi `PI_CODING_AGENT_DIR`. Only the claim epoch is new.
- The claim is a per-entity durable fact and does not depend on `sy` shipping first; the two may land independently.

Ideation must also decide where the claim is stored. Entity frontmatter is the candidate that requires no new object, because `status --set` is then the acquisition surface and every guard already resolves the entity before acting.

## Out of scope

- A cross-session FO-Commander message channel — that is `xp`.
- Captain-authorized active-scope semantics within a single session — that is `sy`.
- A merge claim serializing writes to product `main`. Different lifetime and blast radius; keep it separate and note `mzk` as adjacent.
- Intra-session worker coordination, which `SendMessage` and the roster already cover.

## Acceptance criteria

Ideation fills these in. Each must name a property of the finished entity and a verification that can fail — at minimum, a fixture in which a non-owning session's attempt to mutate a claimed entity is refused, and one proving the refusal names the current owner.

## Test plan

Ideation fills this in. A two-clone real-Git fixture is the likely substrate, reusing the existing two-host state harness rather than building a second one.
