# Debrief 2026-06-05 — Pi subagent stage-dispatch discipline

## Trigger

During the Pi follow-up work after `launcher-binary-path-passthrough`, the FO repeatedly used low-level `pi-subagents` calls directly and had to be corrected by the captain:

- an implementation worker was dispatched with `context: "fork"` instead of fresh context;
- stage assignments were hand-written instead of using the `spacedock dispatch build` artifact as the source of truth;
- the FO stopped after implementation reporting instead of immediately advancing to validation and dispatching an independent validator;
- the implementation report responsibility was misplaced onto the FO instead of the ensign;
- chain mode was used solely to get `phase` / `label`, creating noisy UI.

## Operating corrections

For Spacedock stage dispatches through Pi/subagents:

1. Use the canonical `spacedock dispatch build` artifact as the assignment source of truth. The artifact carries entity slug/name, stage, workflow dir, entity path, worktree path, stage definition fetch command, checklist, and completion/report duties.
2. The Pi/subagent wrapper is additive only: `context: "fresh"`, no `acceptance`, and optional display label/phase where the tool supports it. Do not replace the assignment with a hand-written prompt.
3. Prefer fresh context for all normal implementation/validation/follow-up stage dispatches. Resume/fork is manual/debug only and needs durable metadata/epoch protection.
4. Ensigns own stage reports. The FO reads/verifies them and updates workflow state; it does not author product-stage reports from worker summaries except as an explicit repair of a prior dispatch-contract mistake.
5. After a non-gated, non-terminal stage completes, the FO continues the lifecycle automatically: verify report, advance state, dispatch the next stage. In this workflow, implementation completion should immediately advance to validation and dispatch a fresh independent validator.
6. Async subagent runs are useful to keep the FO unblocked, but use explicit output paths and control thresholds. Do not poll just to wait.
7. Single-agent `pi-subagents` mode currently lacks first-class `phase`/`label`; do not use noisy one-step chain solely for labels unless explicitly desired. Include slug/stage in task/output names until the tool grows label support for single/top-level parallel modes.

## Follow-up entities filed/advanced

- `pi-stage-dispatch-fresh-context` (`d2`): requires explicit `context: "fresh"` and no reliance on worker defaults.
- `pi-stage-dispatch-uses-build-artifact` (`z6`): requires dispatch-build artifacts as assignment source and additive Pi wrapper fields.
- `fo-auto-continues-after-stage-completion` (`wm`): requires FO to continue from non-gated stage completion to next-stage dispatch and defines a test scenario in ideation.

## Product/runtime improvement

A future ergonomic helper should hide the low-level sequence:

- build dispatch artifact;
- construct Pi subagent wrapper with fresh context/no acceptance/label;
- run async with output/control settings;
- record and continue lifecycle.

Potential command shape: `spacedock dispatch continue <slug>` or `spacedock dispatch run --host pi --stage <stage> <slug>`.
