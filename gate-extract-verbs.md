Two deterministic extraction verbs so a weak FO assembles a gate from structured data instead of re-parsing prose. The verdict is NOT computed here; it routes to level-3. Reviewer-tiering and the chosen-direction / natural-place flags were cut after a corpus re-grounding (cycle 2) found they key on shapes that do not persist on disk — see the cut below.

## Problem

Gate preparation today is the model reading a stage report and a `## Acceptance criteria` section and extracting two deterministic structures: the checklist accounting (DONE/SKIPPED/FAILED with the line range each item owns) and each AC's evidence citation scoped to those checklist lines. This is deterministic extraction a binary should own, so a Haiku FO gets the same structured input every time instead of re-deriving it (and mis-deriving it). The third candidate — tiering reviewer findings Material vs Polish — was cut: no stored entity carries a two-tier reviewer block (the Material/Polish tiers are a present-gate *render-time* construct, not persisted input), so there is nothing deterministic to extract.

## Proposed approach

Two deterministic extraction verbs under a new `spacedock gate` command, each reading a stage-report-bearing entity file and emitting the all-strings ordered JSON envelope the workflow already uses (`internal/status/json.go`: every leaf a string, insertion-order keys, compact + newline-terminated). The text default mirrors the JSON for parity, as `--read` does. Neither computes a verdict, and neither carries a flag derived from a shape that does not persist on disk (see "What was cut and why").

**Surface — a new `gate` command, not a `dispatch` subcommand.** `spacedock gate checklist-extract --entity-path FILE --stage STAGE`, `spacedock gate ac-scan --entity-path FILE --stage STAGE`, each `--json` for the envelope. Rationale: `dispatch` builds the worker artifact (the prompt the ensign runs); these verbs read back the completed worker's report at the gate. Different phase of the loop, different noun — a sibling command keeps the surfaces honest. Both verbs share one stage-report parser internally. `--stage` names the gated stage (the same stage value the FO already holds at the gate); it selects which interleaved report to read — see verb 1.

**Verb 1 — `checklist-extract`.** Selects the stage report for the GATED stage, then emits each `- DONE:`/`- SKIPPED:`/`- FAILED:` item with its status, the bullet text, and the 1-based `start`/`end` line range it owns (the bullet line through its trailing evidence line, stopping at the next bullet or the `### Summary`/next-section heading). `start`/`end` use the same 1-based line semantics as `status --read` so the FO can `Read(offset, limit)` an item's evidence.

**Stage-scoped selection (the cycle-2 fix).** Real entities INTERLEAVE stages: `## Stage Report:` headings are append-only and freeform-suffixed (`ideation`, `implementation (cycle 2)`, `validation (cycle 3 — focused re-validation …)`, …). The LAST positional `## Stage Report` is therefore NOT reliably the latest report of the gated stage — verified against `shared-merge-dispatch-contract.md` (archived), whose 14 interleaved sections end in `implementation (go-bare CI alignment)` and `validation (cycle 4 …)`, so a positional-last pick at an `ideation` or `implementation` gate extracts the wrong stage's checklist. The verb instead reads the leading stage-token of each heading (`^## Stage Report: (\S+)` — the first whitespace-delimited word after the colon, before any `(cycle …)` qualifier) and selects the LAST section whose token equals `--stage`. Within that stage's multiple cycles, last-positional-of-that-stage is the latest cycle (append-only ordering). If no `## Stage Report` heading matches `--stage`, the verb fails loudly (AC-5) — it never silently falls back to the positional last.

**Verb 2 — `ac-scan`.** For each `**AC-N**` heading in the entity's `## Acceptance criteria` section, emits the AC id, its 1-based heading line, and a citation list: every `AC-N` token mention **found within a checklist item's line range** (the ranges verb 1 computes for the gated stage), each with the citing line number and line text. An AC with zero such citations is flagged `unevidenced: true`. **The citation search is scoped to checklist evidence lines, never the `### Summary`, `### Feedback Cycles`, or any reviewer prose** — this is the decisive boundary the spike settled: a reviewer *complaining* "AC-2 has no evidence" must not be counted as AC-2 *being* evidenced. **The verb emits the citation map and the `unevidenced` flag; it does NOT decide whether an AC is *satisfied*, and it does NOT decide whether THIS stage was the natural place to evidence that AC.** Whether a red-test citation is evidence-of-failure or evidence-of-progress, and whether an unevidenced AC is a reject signal here versus expected-later, is judgment that routes to level-3.

**What was cut and why (cycle 2 corpus re-grounding).** Two design elements from cycle 1 keyed on shapes that do not persist on disk; the preflight staff review (`docs/roadmap/0205-layered-fo/staff-review.md`, finding `6re`) refuted both against the live corpus, and re-grounding confirmed it:

- **`reviewer-parse` (the whole third verb) is cut.** A `**Reviewer findings:**` Material/Polish block appears in exactly ONE file on disk — this entity itself, describing the verb — and zero real stage reports. The Material/Polish two tiers are a present-gate *render-time* construct (`skills/present-gate/SKILL.md:25,39`, assembly rule 4: "Reviewer findings render in priority tiers"), produced when the FO assembles the gate message, never stored as input the entity body carries. Reviewer output that DOES land on disk lives in `### Feedback Cycles` (46 entities) as free narrative prose with no Material/Polish structure. Retargeting the verb to `### Feedback Cycles` would force a tiering of unstructured prose — exactly the prose-inference the Proof policy bans (`docs/dev/README.md`: "No prose-grep over instruction files"). There is no deterministic two-tier shape to extract, so the verb is cut; tiering reviewer findings stays present-gate render-time work and routes to level-3 as judgment.
- **The `chosen_direction_required` and per-AC `natural_place` flags are cut.** Both were specified as "read from the stage definition, not the report prose." Verified: `spacedock dispatch show-stage-def` has no `--json` and emits the README section as PROSE; the stage definition's `Outputs:` is freeform prose ("A fleshed-out task body with problem statement, proposed approach, acceptance criteria, and a test plan") with NO structured chosen-direction field and NO per-AC Outputs→AC mapping. The README frontmatter `stages:` carries a structured `gate: true` per stage, but `gate`-ness is not the same as a "chosen-direction concept," and there is no field at all from which a per-AC natural-place could be machine-read. present-gate already treats chosen-direction as FO judgment (`SKILL.md:37`). Computing these flags would require either a NEW structured stage-def field (a contract/scaffolding change beyond this member's scope and absent from its doc-diff) or the prose-heuristic the AC itself forbade. Both flags are therefore cut from the verbs and route to level-3 as judgment: L3 reads the gated stage's definition and decides whether a chosen direction is owed and whether an unevidenced AC's natural place is here.

**Why deterministic extraction, not a verdict.** The present-gate assembly rules name these two structures (the checklist roll-up with a line-range citation, and the AC cross-check). A capable FO derives them by reading; a Haiku FO re-derives them unreliably. A binary that returns the same structured input every time removes that variance. The verdict — approve/reject, is-this-AC-satisfied, is-this-chosen-direction-sound, is-this-the-natural-place — stays judgment and routes to level-3 via `fo-tier-delegation`. These verbs feed L3 a clean structured input; they never adjudicate.

## Riskiest-mechanism spike (DONE — exercised on a known-structure fixture, not asserted)

The riskiest unverified path was whether the extractions are actually deterministic over a real stage-report shape AND compose cleanly — specifically whether `ac-scan`'s "is this AC evidenced" can be answered without sliding into the verdict it must not compute. Spiked with a throwaway Go parser (`/tmp/gate-extract-spike/spike4.go`) over a fixture with a KNOWN structure (`/tmp/gate-extract-spike/fixture.md`; a stage report with a DONE, a SKIPPED, and a FAILED item, two ACs where AC-1 is cited in a DONE evidence line and AC-2 is mentioned only in the reviewer findings — line numbers fixed by `cat -n`).

The spike found and settled three design decisions the prose alone would have missed — all three survive the cycle-2 cut and seed the two surviving verbs' first tests:

1. **AC-id token boundary.** A naive split on `-` truncated `AC-1` to `AC`. The id must be tokenized on the heading regex `^\*\*(AC-[0-9A-Za-z]+)\b`, not split on `-`. Confirmed: the corrected parse emits `AC-1`/`AC-2`.
2. **Citation scope.** Scanning the whole `## Stage Report` umbrella swept the `### Summary` and reviewer text, double-counting AC-2 (the reviewer's "AC-2 is unsatisfied" complaint registered as an AC-2 citation — a perverse inversion). Scoping the citation search to the checklist items' own line ranges fixed it: AC-1 cited at line 24 (its DONE evidence), AC-2 cited at `[]` → `unevidenced: true`. This is why the two verbs compose: `checklist-extract`'s line ranges bound `ac-scan`'s search.
3. **Verdict boundary.** AC-2 *is* mentioned in the report, but only as red/unsatisfied. A token-match "evidenced" boolean would mislabel it. The verb therefore emits the raw citation map (with surrounding line text) and the `unevidenced` flag; whether a citation is evidence-of-satisfaction is L3's call. The spike proved the extraction stops exactly at the judgment boundary.

Spike output against the oracle (checklist + AC scan): checklist `DONE [23-24] / SKIPPED [25-26] / FAILED [27-28]`; `AC-1 cited at [24] (unevidenced=false)`, `AC-2 cited at [] (unevidenced=true)`. The line ranges match the fixture's `cat -n` exactly. (The spike also exercised a reviewer Material/Polish block, but that verb is cut — see "What was cut and why"; the reviewer portion of the spike is now moot.)

**What the cycle-1 spike did NOT exercise — the cycle-2 interleaving fix (the new riskiest path).** The spike fixture had ONE stage-report section, so it never exercised stage-scoped selection across INTERLEAVED stages — which the corpus re-grounding showed is the real shape (`shared-merge-dispatch-contract.md`: 14 interleaved `## Stage Report:` sections, ending on an implementation report, not the gated stage). Selecting "the last report whose leading stage-token equals `--stage`" is therefore a NEW mechanism this redesign introduces, NOT covered by the cycle-1 spike. Re-grounding settled the two facts it rests on, against the live corpus, by exercising `grep`/`sort -u` over all `## Stage Report:` headings: (a) the leading token after `## Stage Report: ` is always one of `ideation`/`implementation`/`validation` before any `(cycle …)`/freeform qualifier (every one of the ~150+ distinct headings parses this way), and (b) within a stage the cycles append in order, so last-of-that-stage is the latest cycle. The implementation MUST seed AC-1's first test from an interleaved multi-stage fixture (below), not the single-section spike fixture — that fixture would pass a positional-last bug. This is the one mechanism the cycle-1 spike's known-structure fixture could not have caught, and AC-1 now owns it.

## Acceptance criteria

All criteria are entity-level properties of the finished verbs, each proven by EXERCISING real output against a committed fixture's KNOWN structure (the external oracle — the fixture's `cat -n` line numbers and enumerated contents), never a prose/substring/regex match. The verdict is explicitly NOT asserted by any AC (it is not computed). Every fixture mirrors a shape that EXISTS on the live corpus (interleaved `## Stage Report:` sections, `**AC-N**` headings); no AC keys on a shape that does not persist on disk.

**AC-1 — `checklist-extract` selects the gated stage's latest report (across interleaved stages) and emits each item's status and exact line range.**
Given a committed fixture with INTERLEAVED `## Stage Report:` sections — at minimum an `ideation`, an `implementation`, then a `validation` followed by a LATER `implementation (cycle 2)` so the positional-last section is NOT the gated stage — `gate checklist-extract --entity-path FIXTURE --stage validation --json` selects the `validation` section (not the positional-last `implementation (cycle 2)`) and emits exactly that section's DONE/SKIPPED/FAILED items with their `status` and 1-based `start`/`end` ranges; the ranges, when sliced from the fixture (`lines[start-1:end]`), equal each item's known bullet+evidence text. Items from every other stage's section are absent. For a stage with multiple cycles (`--stage implementation` over the same fixture), the LATEST cycle's items are emitted and the earlier cycle's are absent.
Verified by: Go test slicing the interleaved fixture by each emitted range and asserting byte-equality against the known item text (table-driven over the selected section's items), plus assertions that (a) `--stage validation` does NOT return the positional-last implementation items and (b) `--stage implementation` returns the cycle-2 items, not cycle-1 — a positional-last bug fails (a). The fixture's interleaving is the external oracle.

**AC-2 — `ac-scan` cites AC evidence from the gated stage's checklist lines only and flags the unevidenced AC.**
Given a fixture whose AC-1 is cited in a DONE evidence line of the gated stage's report and whose AC-2 is mentioned ONLY in reviewer/`### Feedback Cycles`/`### Summary` prose, `gate ac-scan --entity-path FIXTURE --stage STAGE --json` emits AC-1 with a citation at the DONE line and `unevidenced: false`, and AC-2 with an empty citation list and `unevidenced: true` (the prose mention is NOT counted). No `satisfied` field and no `natural_place` field is emitted.
Verified by: Go test asserting the citation line numbers against the fixture's known DONE-line position and asserting AC-2's empty citation list / `unevidenced: true`; a mutation test that widening the citation scope to the whole stage report (counting the `### Summary`/reviewer prose) flips AC-2 to evidenced and FAILS the test — proving the scope boundary is load-bearing, not incidental; plus an assertion that the emitted JSON has no `satisfied` and no `natural_place` key.

**AC-3 — A missing or malformed input fails loudly with a non-zero exit and a named diagnostic; never a partial/silent emit.**
A missing `--entity-path`, a missing `--stage`, an unreadable file, an absent `## Acceptance criteria` section, or a `--stage` that matches NO `## Stage Report:` heading exits non-zero with a stderr diagnostic naming the missing input — matching the `show-stage-def` loud-failure idiom (exit 1 / exit 2 for a usage error). It never silently falls back to the positional-last section when the named stage is absent.
Verified by: Go test asserting the exit code and the stderr diagnostic for each missing-input case (no `--entity-path`; no `--stage`; nonexistent file; an interleaved fixture queried with `--stage done` where no `done` report exists → exit non-zero, NOT a silent positional-last emit).
