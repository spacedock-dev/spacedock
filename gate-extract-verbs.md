Extend the EXISTING `status --read` into the one generic markdown-structure helper a weak FO leans on, instead of adding a parallel `spacedock gate` command. Four additions: (a) structured/nested frontmatter output so the `stages:` taxonomy is machine-readable — retiring the boot-time Read-tool + `show-stage-def` kludge; (b) a `--checklist` mode that extracts the gated stage's DONE/SKIPPED/FAILED items with line ranges across interleaved `## Stage Report:` sections; (c) an `--ac-scan` mode that cites each AC's evidence scoped to those checklist lines and flags the unevidenced ones; (d) frontmatter field projection via the EXISTING `--fields` flag, so a caller picks which frontmatter keys come back. The verdict, reviewer-tiering, and chosen-direction call still route to level-3 (the three cycle-2 cuts stand). The captain chose this consolidation over a new command at the cycle-2 gate — and the same anti-proliferation reasoning extends to flags: reuse `--fields`, do not invent a `--read`-specific variant.

## Problem

Gate preparation today is the model reading a stage report and a `## Acceptance criteria` section and extracting two deterministic structures: the checklist accounting (DONE/SKIPPED/FAILED with the line range each item owns) and each AC's evidence citation scoped to those checklist lines. This is deterministic extraction a binary should own, so a Haiku FO gets the same structured input every time instead of re-deriving it (and mis-deriving it).

Separately, the FO boot ALSO re-derives structure by hand. Startup step 4 (`first-officer-shared-core.md:16`) reads the workflow README frontmatter for the stage taxonomy — stage names plus the per-stage `initial`/`terminal`/`gate`/`worktree`/`feedback-to`/`agent` flags — but does it with the Read tool because, as that line says verbatim, "the boot JSON does not carry the stage taxonomy." `status --read <README> --json` *almost* serves this: it already reads any markdown path, is already fence-safe, and already parses flat frontmatter — but it FLATTENS the nested `stages:` map to `"stages": ""` (verified: `status --read docs/dev/README.md --json` emits `"stages": ""`). So the FO falls back to the Read tool plus a separate `dispatch show-stage-def` call for the per-stage prose. Both the gate extraction and the boot taxonomy read are the same shape — deterministic markdown-structure extraction a weak model re-derives unreliably — and `status --read` is the helper that already owns markdown-structure reads.

The third gate candidate — tiering reviewer findings Material vs Polish — was cut (cycle 2): no stored entity carries a two-tier reviewer block (the Material/Polish tiers are a present-gate *render-time* construct, not persisted input), so there is nothing deterministic to extract.

## Proposed approach

Extend the existing `status --read` — NOT a new `spacedock gate` command. `status --read <path>` is already the generic markdown-structure helper: it reads any markdown path (entity, README, skill), is already fence-safe, parses flat frontmatter, and emits the all-strings ordered JSON envelope the workflow uses (`internal/status/json.go`: every leaf a string, insertion-order keys, compact + newline-terminated; the envelope already composes nested objects and arrays via `jsonObj`/`jsonArr`, every leaf still a string). Cycle 1/2 designed these as a parallel `gate` command; the captain chose consolidation at the gate, so they become MODES of `status --read`. Four additions, each gated behind a flag so the default `--read` output is byte-unchanged:

**Addition A — structured frontmatter (`--read <README> --json` surfaces the `stages:` taxonomy).** Today `readSections` calls `ParseFrontmatter`, which deliberately flattens nested mappings/sequences to `""` (`frontmatter.go:124` — "Nested mapping or sequence … empty value"), so `stages:` emits as `"stages": ""`. The package ALREADY has the typed parser: `ParseStagesWithDefaults(path)` (`stages.go:56`, exported) decodes the `stages:` block into ordered `[]Stage` with defaults resolved — `Name`, `Worktree`, `gate`, `terminal`, `initial`, and the optional `feedback-to`/`agent`/`fresh`/`model`. The `--read` JSON emitter (`readJSON`, `json_commands.go:238`, same package) gains a `stages` array: one ordered `jsonObj` per stage with those fields as string leaves, alongside the existing flat `frontmatter` object (the flat object stays — `"stages": ""` within it is harmless; the structured taxonomy lives in the new sibling `stages` array). The text mirror gains one `stage=…` line per stage for parity. **Boot adoption:** Startup step 4 stops Read-tool-ing the README frontmatter and stops calling `dispatch show-stage-def` for the taxonomy; it reads `status --read <README> --json` and consumes the `stages` array for stage names/ordering and the `initial`/`terminal`/`gate`/`worktree`/`feedback-to`/`agent` flags the greet and gate need. (`show-stage-def` survives for what it uniquely carries — the per-stage PROSE Outputs/Good/Bad a dispatch copies into a worker assignment — but it is no longer the boot taxonomy source.)

**Addition B — `--checklist` (`status --read <entity> --stage X --checklist [--json]`).** Selects the stage report for the GATED stage `X`, then emits each `- DONE:`/`- SKIPPED:`/`- FAILED:` item with its status, the bullet text, and the 1-based `start`/`end` line range it owns (the bullet line through its trailing evidence line, stopping at the next bullet or the `### Summary`/next-section heading). `start`/`end` use the SAME 1-based line semantics `status --read` already emits for headings, so the FO can `Read(offset, lines)` an item's evidence — the consolidation makes this a literal shared semantic, not just a parallel one.

**Stage-scoped selection (the cycle-2 design, carried forward verbatim).** Real entities INTERLEAVE stages: `## Stage Report:` headings are append-only and freeform-suffixed (`ideation`, `implementation (cycle 2)`, `validation (cycle 3 — focused re-validation …)`, …). The LAST positional `## Stage Report` is therefore NOT reliably the latest report of the gated stage — verified against `shared-merge-dispatch-contract.md` (archived), whose 14 interleaved sections end in `implementation (go-bare CI alignment)` and `validation (cycle 4 …)`, so a positional-last pick at an `ideation` or `implementation` gate extracts the wrong stage's checklist. `--checklist` instead reads the leading stage-token of each heading (`^## Stage Report: (\S+)` — the first whitespace-delimited word after the colon, before any `(cycle …)` qualifier) and selects the LAST section whose token equals `--stage`. Within that stage's multiple cycles, last-positional-of-that-stage is the latest cycle (append-only ordering). If no `## Stage Report` heading matches `--stage`, the mode fails loudly (AC-5) — it never silently falls back to the positional last.

**Addition C — `--ac-scan` (`status --read <entity> --stage X --ac-scan [--json]`).** For each `**AC-N**` heading in the entity's `## Acceptance criteria` section, emits the AC id, its 1-based heading line, and a citation list: every `AC-N` token mention **found within a checklist item's line range** (the ranges `--checklist` computes for the gated stage), each with the citing line number and line text. An AC with zero such citations is flagged `unevidenced: true`. **The citation search is scoped to checklist evidence lines, never the `### Summary`, `### Feedback Cycles`, or any reviewer prose** — this is the decisive boundary the spike settled: a reviewer *complaining* "AC-2 has no evidence" must not be counted as AC-2 *being* evidenced. **The mode emits the citation map and the `unevidenced` flag; it does NOT decide whether an AC is *satisfied*, and it does NOT decide whether THIS stage was the natural place to evidence that AC.** Whether a red-test citation is evidence-of-failure or evidence-of-progress, and whether an unevidenced AC is a reject signal here versus expected-later, is judgment that routes to level-3.

**Addition D — frontmatter field projection via the EXISTING `--fields` flag (`status --read <entity> --fields status,verdict`).** Today `--read` always returns the WHOLE frontmatter map AND actively REJECTS the flag: verified, `status --read <entity> --fields status,verdict` exits 1 with `Error: --read cannot be combined with --fields/--all-fields` (the mutual-exclusion guard at `native_runner.go:338-340,357`). `--fields` already projects frontmatter keys for `status --where`/`--next --json` (the event loop reads `--where 'pr !=' --json --fields id,slug,pr`); `resolveJSONFields`/`entityJSONObj` (`json_commands.go:16,46`) project to exactly the named keys in their named order. Implementation: REMOVE the `hasFieldsFlag` branch from `--read`'s incompatibility list, plumb the parsed fields into `runReadSection`, and project `sr.frontmatter` through the same field-resolution (`resolveJSONFields`, which with explicit `--fields` returns the named list verbatim) and the same projection SEMANTICS as `entityJSONObj` (named keys in their named order, a missing key projecting an empty string) — via a frontmatter-map projection loop mirroring `entityJSONObj`, NOT a call into it (`readJSON` has no `*entity`; `entityJSONObj` reads `e.fields[f]` off an entity, so the projection is a parallel loop over `sr.frontmatter`, not the same code). So `--read <entity> --fields status,verdict --json` emits a `frontmatter` object containing exactly `status` and `verdict` (in that order), omitting the rest. No flag → the whole map, as today. This is a reuse, not a new flag — the same anti-proliferation discipline that dropped the `gate` command: one `--fields`, consistent across `--where`/`--next`/`--read`, not a `--read`-specific variant. A missing key projects an empty-string value exactly as `--where`/`--next` already do (the same projection semantics, a parallel loop mirroring `entityJSONObj`).

**Interaction with Addition A (`--fields` selects keys; the nested-output change controls shape).** The two compose on orthogonal axes: `--fields` picks WHICH flat-frontmatter keys the `frontmatter` object carries; Addition A's structured `stages` array is a SEPARATE top-level sibling whose presence is controlled by the `stages:` block existing, NOT by `--fields`. So `--fields status` projects the flat `frontmatter` to `{status}` and does not suppress or include the `stages` array (the array is structural read output, like `headings`, not a frontmatter key). Concretely: `--fields stages` projects the flat scalar key `stages` (value `""`, the flattened form) — it does NOT reach into or reshape the structured `stages` array, because `--fields` is a key selector over the flat map, matching its `--where`/`--next` meaning exactly. A caller wanting the taxonomy reads the `stages` array; a caller wanting a frontmatter subset uses `--fields`. Keeping these axes separate is what preserves `--fields`'s single consistent meaning across all three read surfaces.

Both gate modes (`--checklist`, `--ac-scan`) require `--stage` and share the one stage-report parser internally; without a mode flag, `status --read` behaves exactly as today.

**What was cut and why (cycle 2 corpus re-grounding).** Two design elements from cycle 1 keyed on shapes that do not persist on disk; the preflight staff review (`docs/roadmap/0205-layered-fo/staff-review.md`, finding `6re`) refuted both against the live corpus, and re-grounding confirmed it:

- **`reviewer-parse` (the whole third verb) is cut.** A `**Reviewer findings:**` Material/Polish block appears in exactly ONE file on disk — this entity itself, describing the verb — and zero real stage reports. The Material/Polish two tiers are a present-gate *render-time* construct (`skills/present-gate/SKILL.md:25,39`, assembly rule 4: "Reviewer findings render in priority tiers"), produced when the FO assembles the gate message, never stored as input the entity body carries. Reviewer output that DOES land on disk lives in `### Feedback Cycles` (46 entities) as free narrative prose with no Material/Polish structure. Retargeting the verb to `### Feedback Cycles` would force a tiering of unstructured prose — exactly the prose-inference the Proof policy bans (`docs/dev/README.md`: "No prose-grep over instruction files"). There is no deterministic two-tier shape to extract, so the verb is cut; tiering reviewer findings stays present-gate render-time work and routes to level-3 as judgment.
- **The `chosen_direction_required` and per-AC `natural_place` flags are cut.** Both were specified as "read from the stage definition, not the report prose." Verified: `spacedock dispatch show-stage-def` has no `--json` and emits the README section as PROSE; the stage definition's `Outputs:` is freeform prose ("A fleshed-out task body with problem statement, proposed approach, acceptance criteria, and a test plan") with NO structured chosen-direction field and NO per-AC Outputs→AC mapping. The README frontmatter `stages:` carries a structured `gate: true` per stage, but `gate`-ness is not the same as a "chosen-direction concept," and there is no field at all from which a per-AC natural-place could be machine-read. present-gate already treats chosen-direction as FO judgment (`SKILL.md:37`). Computing these flags would require either a NEW structured stage-def field (a contract/scaffolding change beyond this member's scope and absent from its doc-diff) or the prose-heuristic the AC itself forbade. Both flags are therefore cut from the verbs and route to level-3 as judgment: L3 reads the gated stage's definition and decides whether a chosen direction is owed and whether an unevidenced AC's natural place is here.

**Why deterministic extraction, not a verdict.** The present-gate assembly rules name these two structures (the checklist roll-up with a line-range citation, and the AC cross-check). A capable FO derives them by reading; a Haiku FO re-derives them unreliably. A binary mode that returns the same structured input every time removes that variance. The verdict — approve/reject, is-this-AC-satisfied, is-this-chosen-direction-sound, is-this-the-natural-place — stays judgment and routes to level-3 via `fo-tier-delegation`. These modes feed L3 a clean structured input; they never adjudicate.

## Acceptance criteria

All criteria are entity-level properties of the extended `status --read`, each proven by EXERCISING real output against a committed fixture's KNOWN structure OR the REAL workflow README (the external oracle — the fixture's `cat -n` line numbers / enumerated contents, or the README's actual `stages:` block), never a prose/substring/regex match. **AC-1 — `status --read … --stage X --checklist` selects the gated stage's latest report (across interleaved stages) and emits each item's status and exact line range.**
Given a committed fixture with INTERLEAVED `## Stage Report:` sections — at minimum an `ideation`, an `implementation`, then a `validation` followed by a LATER `implementation (cycle 2)` so the positional-last section is NOT the gated stage — `status --read FIXTURE --stage validation --checklist --json` selects the `validation` section (not the positional-last `implementation (cycle 2)`) and emits exactly that section's DONE/SKIPPED/FAILED items with their `status` and 1-based `start`/`end` ranges; the ranges, when sliced from the fixture (`lines[start-1:end]`), equal each item's known bullet+evidence text. Items from every other stage's section are absent. For a stage with multiple cycles (`--stage implementation` over the same fixture), the LATEST cycle's items are emitted and the earlier cycle's are absent.
Verified by: Go test slicing the interleaved fixture by each emitted range and asserting byte-equality against the known item text (table-driven over the selected section's items), plus assertions that (a) `--stage validation` does NOT return the positional-last implementation items and (b) `--stage implementation` returns the cycle-2 items, not cycle-1 — a positional-last bug fails (a). The fixture's interleaving is the external oracle.

**AC-2 — `status --read … --stage X --ac-scan` cites AC evidence from the gated stage's checklist lines only and flags the unevidenced AC.**
Given a fixture whose AC-1 is cited in a DONE evidence line of the gated stage's report and whose AC-2 is mentioned ONLY in reviewer/`### Feedback Cycles`/`### Summary` prose, `status --read FIXTURE --stage STAGE --ac-scan --json` emits AC-1 with a citation at the DONE line and `unevidenced: false`, and AC-2 with an empty citation list and `unevidenced: true` (the prose mention is NOT counted). No `satisfied` field and no `natural_place` field is emitted.
Verified by: Go test asserting the citation line numbers against the fixture's known DONE-line position and asserting AC-2's empty citation list / `unevidenced: true`; a mutation test that widening the citation scope to the whole stage report (counting the `### Summary`/reviewer prose) flips AC-2 to evidenced and FAILS the test — proving the scope boundary is load-bearing, not incidental; plus an assertion that the emitted JSON has no `satisfied` and no `natural_place` key.

**AC-3 — `status --read <README> --json` surfaces the nested `stages:` taxonomy as a structured array, and the plain `--read` output is otherwise byte-unchanged.**
Given the REAL `docs/dev/README.md`, `status --read docs/dev/README.md --json` emits a `stages` array of ordered objects whose entries equal the README's actual stages — `backlog` (`initial: true`, `gate: true`), `ideation` (`gate: true`), `implementation` (`worktree: true`), `validation` (`gate: true`, `worktree: true`, `feedback-to: implementation`, `fresh: true`), `done` (`terminal: true`) — every leaf a string, in declaration order. Without the new behavior, the same call emits `"stages": ""` (the flattened scalar) and no `stages` array. The existing `headings` array, `total_lines`, and flat `frontmatter` object are unchanged.
