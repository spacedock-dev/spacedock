The boot-resident FO core (`skills/first-officer/references/first-officer-shared-core.md`) loads ~675 tokens of phase-specific reference at greet that isn't needed until a specific phase: the **Status Viewer** section (~657 tok — `status --set` field docs, the canonical invocations, the Captain-Facing State Display rendering — needed only when answering an ad-hoc status question or mutating state) and **Issue Filing** (~18 tok — rare). Defer both into one lazily-loaded `entity-status` reference, loaded on first status-query / mutate / issue-file, using the same name-a-pointer / defer-the-body pattern the dispatch and merge modules already use. Sibling to z4's Dispatch/Merge pointer consolidation, which provides the registry index.

Measured: ~675 tok ≈ 9–10% of the ~7,170-token boot core (part of the ~32% total deferrable surface; FO Write Scope / ID Styles / Probe discipline are separate sibling tasks).

## Design — what moves and the boot-core pointer

**What leaves the boot core (verbatim, into `skills/first-officer/references/fo-status-viewer.md`):**
- The whole `## Status Viewer` section (today lines 35–70): the `${SPACEDOCK_BIN:-spacedock} status` launcher intro, the invocation block + the full query/mutate flag docs (`--boot`, `--validate`, `--resolve`, `--next-id`, `--next`/`--where`), the `--set` field docs, and the `### Captain-Facing State Display` subsection (the canonical invocations + the output-rendering guidance). ~666 tok.
- The whole `## Issue Filing` section (today lines 232–234): "Do not file GitHub issues without explicit human approval." ~19 tok. It rides the same reference + pointer (deferring it alone would be occupancy-POSITIVE: the rule is shorter than any pointer to it; bundled, its marginal cost is ~0).

The reference is **host-neutral — no per-host adapter** (unlike `fo-dispatch-core.md` / `fo-merge-core.md`, which pair a core with a runtime-adapter section). It is pure `status`-command + filing reference, identical on Claude/Codex/Pi.

**The boot-core pointer (replaces `## Status Viewer` at line 35; `## Issue Filing` is deleted):**

```
## Status Viewer and Issue Filing (deferred module)

- → reference: `references/fo-status-viewer.md` (host-neutral; no per-host adapter), loaded at the FIRST status query, `--set` mutation, `--next-id`/`--resolve` lookup, or GitHub-issue filing.
- done-when: the FO answers an ad-hoc status question, mutates frontmatter via `--set`, previews/resolves an id, or files a GitHub issue — the `status` query/mutate command surface (flag docs, the canonical captain-facing invocations, the Captain-Facing State Display rendering) and the issue-filing approval gate are resident.
- guard: a greet-and-stop boot reads neither — the greet composes its summary from `«state.boot»` JSON + README frontmatter (Startup step 8) and presents any ready gate via `present-gate`; no boot-resident path reaches the Status-Viewer display rules.
```

This is the same `## … (deferred module)` heading + `→`/`done-when`/`guard` shape as Dispatch/Merge, so z4's #6 registry can fold it uniformly. **Open arrow-taxonomy decision (gate + z4):** `→ runtime-binding` is defined as "defers to the host adapter," which this reference does NOT — it has no adapter. I propose a `→ reference` form (a host-neutral deferred-reference load point) rather than overloading `runtime-binding`. k4 faces the identical question (its Write-Scope/ID-Styles reference is also adapter-less); the two new pointers should use the same label, and z4 (which owns the `runtime-support.md` sync + the registry) classifies it. The closure test keys on the `references/*.md` path, not the arrow label, so AC-3 is unaffected by the label choice.
