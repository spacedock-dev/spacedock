Sibling to `entity-status`. ## Riskiest-mechanism spike (AC-2, load-bearing) — DONE

**Claim under test:** deferring `## FO Write Scope` out of the boot core must NOT break the boot's own `«state.sweep-merged»` write path (terminalize verdict=PASSED / archive / remove-worktree at boot when a merged PR exists). The risk: if that path read the Write-Scope prose to authorize itself, deferral would silently break boot.

**Result — the sweep write is binary-self-authorizing, not prose-authorized.** The boot sweep splits into a read-only DETECT and a binary FINALIZE, neither of which reads Write-Scope prose. The finalize commands are `status --set`/`status --archive` (the pr-merge mod startup hook, `_mods/pr-merge.md:17–20`), **not** `merge guard` — the staff review (M8) corrected the original spike, which cited `merge guard`; the conclusion (self-authorizing) is unchanged because `--set`/`--archive` are equally binary. Re-pointed evidence (all green, re-run this ideation):
- `internal/status/verdict_guard_test.go::TestVerdictGateFinalizeWithVerdictAllowed` drives `status --set 002-vendor-script status=done completed verdict=passed worktree=` in a bare `seq-workflow` fixture (no `skills/`, zero Write-Scope prose) → entity terminalizes with `status: done`, `verdict: passed`. `::TestVerdictGateArchiveWithVerdictAllowed` drives `status --archive` on a verdicted terminal entity → archives. **`runSet`/`runArchive` finalize with no FO Write Scope section anywhere on disk.**
- `internal/status/archive_guard_test.go::TestTerminalSetUnderModBlockRejected` pins the two-step precondition — terminalizing under a pending `mod-block` is refused with "Clear mod-block in a separate --set call" — exactly why the mod hook clears `mod-block=` first, then terminalizes.
- `internal/cli/state_sweep_test.go::TestStateSweepIsReadOnly` → `spacedock state sweep` makes no commit/push/mutation. **Detection is read-only; the write is `runSet`/`runArchive`.**

**Trace confirming the chain stays resident/binary after the cut:** Startup step 7 → `«state.sweep-merged»()` (boot-resident, first-officer-shared-core.md:165–171, NOT in either deferred section) → reads `_mods/pr-merge.md` → its startup hook delegates the finalize to `status --set {slug} mod-block=`, `status --set {slug} completed verdict=PASSED worktree=`, then `status --archive {slug}` (mod lines 17–20). `«state.sweep-merged»` binds `→ shipped: spacedock state sweep` — the read-only DETECT (`internal/cli/state_sync.go::runStateSweep`, "makes no commit, push, or mutation"); the WRITE is `runSet` (`internal/status/handlers.go:20`) + `runArchive` (`internal/status/mutate.go:275`). **No node in this chain names `## FO Write Scope`, and `merge guard` (the deferred `fo-merge-core.md` terminal ceremony) is not on the boot path at all.** The Write-Scope section declares what the FO may *hand-write* on main; the boot sweep's writes are binary-executed and need no such declaration loaded.

**No spike needed for the greet-no-load pattern itself:** it reuses the already-proven Dispatch/Merge deferred-module guard (a greet-and-stop boot traverses Startup 1–8 + `«state.*»` only, which name no deferred-module load point). The only NEW risk was the boot's own write path — spiked above.
