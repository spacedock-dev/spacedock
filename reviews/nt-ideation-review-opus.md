## Material findings

### M-A. The refined discriminator's "loads adapter section alongside at the trigger" clause is FALSE for `merge` on Claude — AC-5's precision deliverable is undermined by its own wording.

The design's M3 "refinement" (Part A `:34`, AC-5 `:122`) states: *"a deferred module that loads a per-host adapter section ALONGSIDE its core at the trigger (dispatch/merge → `claude-fo-dispatch.md`) stays a reference; a module whose host binding is already boot-resident or absent AT ITS LOAD POINT realizes as a skill."* It lumps dispatch and merge together as "load claude-fo-dispatch.md alongside the core at the trigger."

Ground truth — `skills/first-officer/references/claude-first-officer-runtime.md:11-13` (`## Terminal teardown`):
> "The Claude cooperative-shutdown call is the per-name `SendMessage(shutdown_request)` in `## Terminal Worker Teardown` of `references/claude-fo-dispatch.md` (**already loaded at first dispatch**) — **there is no separate Claude merge reference**."

So at the merge trigger (terminal boundary), NO per-host adapter section loads alongside `fo-merge-core.md` — the Claude teardown was loaded at *first dispatch*, not at terminalization. Merge's host binding at its load point is therefore neither "loaded alongside at the trigger" (clause 1, the design's stated basis) NOR "boot-resident or absent" (clause 2). It falls between the two clauses. The design's specific justification for classifying merge as a reference is factually contradicted by the shipped Claude adapter.

Why this matters: the classification OUTCOME (merge → reference) is still correct — but only under a *different*, cleaner principle than the one the design writes down: **host binding lives in a boot-resident section → skill; host binding lives in a deferred reference file → reference (regardless of when that file loads).** Under that principle: write-core's `spacedock new` binding is in `## Filing New Entities`, which IS boot-resident (`claude-first-officer-runtime.md:1-3,33-35` — the whole file is "the boot-resident runtime adapter") → skill ✓; merge's teardown is in the deferred `claude-fo-dispatch.md` → reference ✓; dispatch likewise → reference ✓; status-viewer has no host binding → skill ✓. All four hold under *this* wording, with no edge case.

AC-5's entire deliverable is "`docs/runtime-support.md` states the discriminator **precisely**." The current formulation does not survive the merge case, and cycle-2's M3 note claims it "sharpened the discriminator to survive write-core's own adapter binding" — but the identical logic, applied to merge, exposes that the "loads alongside at the trigger" proxy is still imprecise. Note `fo-merge-core.md:3` ("the runtime adapter supplies the host's concrete terminal teardown … read alongside this file") is *symmetric* to `fo-write-core.md:7` ("the host `spacedock new` invocation form is the runtime adapter's new-entity binding, read alongside this file") — both say "read alongside," yet the design classifies one as skill and one as reference. The only thing that actually separates them is boot-resident-vs-deferred binding, not the trigger-loading language the design uses.

Fix (no redesign): reword the discriminator in Part A `:34`, AC-5 `:122`, and the target `docs/runtime-support.md:21` edit to key on **boot-resident-vs-deferred binding location**, not "loads alongside at the trigger." The 2-skills/2-references shape is correct; only the stated rule needs to match the shipped mechanism.

### M-B. AC-2's ensigncycle surgery is under-enumerated, and the load-bearing later-delta control for the new `SkillNames` field is not carried over — on the design's own riskiest path, over a codebase with a documented scar for exactly this false-pass.

The "only two contractlint tests couple to the registry shape" claim is ACCURATE (see V-1 below). But the AC-2 oracle switch touches a *third* coupling family in `internal/ensigncycle/` that the design addresses at the mechanism level yet under-names concretely, and one omitted piece is load-bearing.

Ground truth — the retired-oracle surface (`grep assertGreetReadsNoDeferredStatusReference|deferredStatusReference`):
- `shallow_boot_measure_test.go:14` — `const deferredStatusReference = "fo-status-viewer.md"` (the hard-coded target).
- `shallow_boot_measure_test.go:104` — the `assertGreetReadsNoDeferredStatusReference` definition (keys on `ClaudeTurn.ReadTargets`).
- `shallow_boot_measure_unit_test.go:79-86` — `TestAssertGreetReadsNoDeferredStatusReferenceOffline` (file fixtures).
- `shallow_boot_measure_unit_test.go:88-102` — `TestAssertGreetReadsNoDeferredStatusReferenceCatchesLaterDeltaRead` (**INLINE** later-delta fixture, lines 96-98, reads `fo-status-viewer.md` on delta[1]).
- `claude_live_runner_test.go:346` — the live call.

The design names the live call at `:346`, the two file fixtures (`shallow-boot-greet.stream.jsonl` augmented, `greet-reads-status-viewer.stream.jsonl` → `greet-invokes-fo-status-viewer-skill.stream.jsonl`), the new `SkillNames` field, and the new oracle — but does NOT name `shallow_boot_measure_test.go` (const + definition) or the **inline later-delta control** at `shallow_boot_measure_unit_test.go:88-102`.

That inline control is not incidental. `ParseClaudeTurns` merges *later-delta* tool_use into a turn (`internal/journeymetrics/claude.go:213-219` merges `ToolNames` AND `ReadTargets`); the entire multi-delta merge exists because a first-delta-only parse previously produced a *hollow* AC-2 false-pass (documented in-code at `shallow_boot_measure_unit_test.go:47-48,92-93` and `claude.go:159-162`). A `Skill` tool_use block can land on a later delta exactly like a `Read` or `TeamCreate`. So the new `SkillNames` field MUST be (a) extracted in the per-block loop (`claude.go:199-212`) and (b) merged in the later-delta branch (`claude.go:217-218`), and it needs a later-delta RED control — otherwise the greet-independence proof for the new skill oracle is hollow in precisely the way the codebase already got burned on. The design's spike frames the extractor as "one line — `jsonStringField(input,"skill")`"; that is true for the *extraction* (the helper exists at `readadoption.go:135`, and `readToolTarget` extracts `Read`'s `file_path` identically at `:124`), but it undersells the field wiring (add-field + per-delta merge + control test), and retiring the Read-based later-delta control without a Skill-based equivalent is a coverage regression on the riskiest path.

Mitigant (why FIXES, not REDESIGN): if the implementer wires `SkillNames` parallel to `ReadTargets` (same loop, same merge line), the later-delta merge is inherited for free, and `AC-4`'s `go test ./internal/ensigncycle/` gate turns any missed retired-oracle call site into a compile error. So the mechanism will very likely work — but the design should explicitly (1) name `shallow_boot_measure_test.go` + `shallow_boot_measure_unit_test.go` as edit sites and (2) require a later-delta `Skill(fo-status-viewer)` RED control mirroring `TestAssertGreetReadsNoDeferredStatusReferenceCatchesLaterDeltaRead`, rather than folding it under a generic "offline RED/GREEN unit fixtures."
