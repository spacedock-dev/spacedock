## Proposed approach

The 16-instance ledger reduces to three failure mechanisms once the discovery "race" is diagnosed (see Spike record: it is NOT a race). Each is fixed at its root in the live-test harness and its fixtures; the binary is correct and gets no change.

**Root-cause map** (each of PR #488's 7 baseline scenarios traces to one of these):

1. **Wrong-root cd-wander** (instances 3-6, 8-9, 13-15; both models). Every drive prompt names the workflow only as `Workflow directory: .` (all 9 builders in `shared_fixtures_test.go`); the absolute root reaches the FO only via `cmd.Dir = workflowRoot` (`claude_live_runner_test.go:463`). Once the FO `cd`s before it boots, the `.` anchor is gone and it operates outside the fixture. The wrong-root detector (`detectWrongRootBoot`, wired at `claude_live_runner_test.go:518`) already reds this legibly — so the value-AC's "distinct diagnostic" half is already met for this shape; the gap is that it fails the scenario instead of reaching it.
2. **Contract-file find-hunt** (instances 7, 8, 11, 16). After reading the fixture the FO greps the filesystem for a contract reference file (`fo-merge-core.md`, `claude-fo-dispatch.md`) that lives in the `--plugin-dir` checkout, never the fixture, then stalls past the 60s no-progress budget. Today this surfaces as an OPAQUE `made no stream progress` stall, indistinguishable from a genuine mid-scenario hang. The claude runner does NOT run the existing `detectBroadSearchAtBoot` (only `zero_discover_live_test.go:112` does).
3. **Discovery false-negative** (instances 10, 12, 13-15). `status --boot --identify` returns "no commissioned Spacedock workflow found" and the FO correctly stops — failing the scenario as its OWN assertion. The Spike proves this is deterministic, not a race: only 2 of 10 fixture READMEs carry the production `commissioned-by: spacedock@` marker that discovery requires (`handlers.go:546`), so `--boot --identify` deterministically false-negatives on the other 8, while `--workflow-dir .` (which bypasses discovery) succeeds on all. The nondeterminism is in the FO's CHOICE between those two boot paths, not the binary's response.

**The fix — three changes, all in the harness/fixtures:**

- **(A) Anchor the drive prompt.** In the eight NON-boot-subject prompt builders (`gatePrompt`, `rejectionPrompt`, `escalationPrompt`, `mergeHookGuardPrompt`, `filingPrompt`, `mergeTriagePrompt`, `smallestMechanismPrompt`, `keepMovingPrompt`), replace `Workflow directory: .` with the ABSOLUTE fixture root the runner already knows (`workflowRoot`, threaded into the builder). A realism fix — production FOs are told their workflow path — that gives an anchor a stray `cd` cannot erase. It deliberately does NOT add "do not cd / do not search" imperatives: those duplicate the FO's own boot contract and would MASK a contract-adherence regression.
- **(B) Give the fixtures the production discovery marker.** Add `commissioned-by: spacedock@1` to every fixture README whose scenario expects a discoverable workflow (the 8 that lack it: gate, rejection, escalation, merge-hook, shallow-boot, merge-triage, keep-moving in `shared_fixtures_test.go`, plus `gateStopReadme` in `live_gate_stop_test.go`). Spike-proven to make `--boot --identify` resolve deterministically, so the FO's path choice can no longer produce a scenario-failing false-negative. `TestLiveZeroDiscoverReportsAndStops`'s fixture is the sole opt-out — its SUBJECT is non-discovery, so it stays markerless.
- **(C) Make the find-hunt red as a preamble fumble.** Wire the existing `detectBroadSearchAtBoot` into `claudeLiveRunner.run`'s failure path, immediately after the `detectWrongRootBoot` check (`claude_live_runner_test.go:518-526`), with a scenario-neutral message (the detector's current message is zero-discover-specific). A contract-file `find /` hunt then reds fast with "FO broad-searched the filesystem at boot" naming the sweep, instead of an opaque 60s stall. Does NOT mask — it keeps the fumble a RED, only legible and fast.

**Opt-out set (boot behavior is the SUBJECT — no anchor):** `TestLiveDefaultHeadlessStopsAtGate` (default-headless drive-to-gate), `shallow-boot` (no-TeamCreate-before-greet / S7b sweep), `TestLiveZeroDiscoverReportsAndStops` (report-and-stop). These keep `Workflow directory: .` so their orientation is tested unaided. gate-stop and shallow-boot still receive the marker (B): the marker makes the workflow findable at the CORRECT root without masking whether the FO reaches that root, and the wrong-root detector still catches a wander regardless of the marker.

**Binary side — explicit, justified scope-narrowing (no code change):**

- **REJECT** the seed's proposed `status --boot --identify` "close the discovery-race window" change. The Spike disproves the race: the false-negative is a deterministic fixture-realism gap (missing marker), the binary behaves correctly, and the fix belongs in the fixture (B).
- **DEFER** the `state sweep` / `state ready` flag-tolerance rider. It addresses only the single codex shallow-boot instance, not the measured PR #488 sonnet baseline; the four guessed flag shapes were never recorded, so we would design blind; and the tv default-to-stage precedent (`gate_extract.go:36`) covers defaulting an OMITTED arg (`state sweep --workflow-dir .` already works and already defaults via `ResolveWorkflowDir`) — it does not extend to accepting arbitrary WRONG flags. Follow-up: needs the exact guessed shapes captured before it can be designed.
- **DEFER** the boot-preamble RETRY (re-launch on a preamble-classified failure). Higher risk (misclassification could mask a real regression) and unnecessary — A+B+C address every scenario in the measured baseline. Held as the escalation lever if the live rate (AC-3) stays high after A+B+C land.

No user-visible / CLI / docs-site surface changes — all edits are to `internal/ensigncycle/*_test.go` harness and fixtures. No doc diff required.

## Spike record

**Riskiest mechanism:** whether the "discovery-race false-negative" (instances 10, 12, 13-15) is a binary race (needing a binary fix) or a deterministic fixture-marker mismatch (fixable in the fixture). The entire binary-side scope-narrowing rests on this.

**Exercised (CLI, no model):** built a minimal fixture mirroring `gateReadme`/`mergeTriageReadme` (no `commissioned-by`), git-init'd it, and ran `spacedock status --boot --identify` from it. Result — deterministic, not a race:
- WITHOUT the marker: 5/5 runs → exit 1 "no commissioned Spacedock workflow found …".
- `status --boot --workflow-dir . --json` (bypasses discovery), same markerless fixture: 3/3 → exit 0 boot JSON. This is the path the FO takes when the scenario PASSES; the failure is purely the FO choosing `--boot --identify` instead.
- AFTER adding `commissioned-by: spacedock@1`: 5/5 runs of `--boot --identify` → exit 0, deep-boot JSON.

**Conclusion:** the false-negative is a deterministic marker mismatch; adding the marker (fix B) eliminates it; no `status --boot --identify` binary change is warranted. This spike is AC-1's first test. Discovery predicate confirmed at `internal/status/handlers.go:546` / `discover_walkup.go:26` (`strings.HasPrefix(commissioned-by, "spacedock@")`).

**No spike needed for the other mechanisms:**
- Fix C rests on `detectBroadSearchAtBoot`, already offline-proven (`broad_search_detect_test.go`: `repo_rooted_find_reds`, `find_path_arg_less_reds`; plus the real-stream replays in `zero_discover_replay_test.go`); the change is only WIRING it into the claude runner's existing failure path.
