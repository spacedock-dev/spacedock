A gate approval on a terminal-target stage (`validation → done`) is *immediately consumable into terminal status*: the binding approval's authority is marked spent (`consumed=true`) and the entity's status flips to `done` at consume time, while delivery (PR push, CI, merge) and workflow terminal fields (`verdict`, `completed`) remain pending. Three desyncs follow:

1. **Authority is spent before the spend is justified.** The consumed approval is irrevocable by design ("never double-applied"), yet the deliverable it ratified is only *pending* — there is no delivery proof at the moment the approval is spent.
2. **Two status classes per entity.** `status=done` (decision monoid) with empty `verdict`/`completed`/`pr` (delivery incomplete). The mod-block guard withholds terminal fields deliberately, but the status field itself already claims terminal. CL feedback: "right now if it's done it can't be sent back."
3. **No regression verb exists.** If the PR fails (CI red, closed-unmerged, a new defect uncovered), the workflow's own pre-done `feedback-to: implementation` wiring is *inert* (it's scoped to pre-done rejections). The pr-merge mod's answer to a closed PR is literally "report to the captain and wait"; the only physical reverse routes are frontmatter surgery or a second gate cycle that would have to dance around the consumed record. Prior live precedent (`worktree-clear-guard-misfire-on-backward-route`) shows even bookkeeping of a backward route trips the same merge-hook guard.

The pure-`merge: local` workflow hides this; any PR-gated workflow exposes it. Three review rounds missed it because they scoped to the API of gates, not the failure mode of delivery-after-consume.

## Problem

The consumption semantic treats "terminal-stage approval" and "terminal delivery" as one event; they are two, and the second can fail. Concretely, today:

1. **One atomic write, one irreversible spend.** `gates.Consume` (`internal/gates/application.go`) co-writes `application.state: consumed` and `status: done` in a single entity replacement for a terminal-target approval. The authority ledger and the workflow status both claim completion at the same instant, while the pr-merge mod deliberately withholds `verdict`/`completed` behind the merge-hook guard. Authority is spent with zero delivery proof in hand.
2. **Two status classes, one field.** A `status=done` entity is either *delivered* (verdict/completed set, archived or archivable) or *done-but-undelivered* (PR open/unpushed/CI unknown). Nothing in frontmatter distinguishes them without composing status + mod-block + pr + verdict — and CL's operational rule is "if it's done it can't be sent back," so the second class is a dead end.
3. **No recorded reverse route.** `applicationForDecision` wires `revise` to `feedback-to` only for pre-done gate rejections. The application's durable state enum (`pending/consumed/superseded/not-applicable` in `model.go::validateApplication`) has no value for "delivery failed after approval," `ValidateTransition` freezes closed attempts, and the only physical routes backward are frontmatter surgery or a second gate cycle that must dance around the consumed record (both rejected in the filing). The pr-merge mod's CLOSED-PR answer — "report to the captain and wait" — has no verb behind it.

The pure-`merge: local` workflow hides the hole (delivery is local and synchronous inside the terminal ceremony, so the window between spend and proof is small). Any PR-gated workflow exposes it. The model must make approval-authority, stage status, and terminal fields cohere in BOTH directions of the consume/delivery boundary: forward (spend lands only with delivery proof) and backward (a failed delivery is a recorded state transition, never surgery; re-entry runs as a normal successor gate attempt with a *fresh* approval — the old authority is superseded, never re-spent).

## Proposed approach

**Pending-preserving consume; `merge guard` as the sole terminal consumer; the existing `pending→superseded` as the send-back.** One rule for every terminal approval regardless of merge policy or hook registration: `gate consume` never spends a terminal-target approval and never writes terminal status. This is the captain's six-point minimum (his revise resolution, cycle 1 below) taken as the whole design. Nothing is added beyond the six points except one refusal the transaction itself requires (argued below); no `delivering`, no `reversed`/`reversal`, no `--to`, no actor flag, no compatibility path, no scanner rewrite, no lock work.

### The minimal transaction (the entire mechanism)

1. **Consume routes, does not spend — and carries no hook knowledge.** `gate consume` on an approval whose target stage is terminal leaves `application.state: pending`, leaves `status` at the gated stage, and returns the route `approved-awaiting-merge`: consume is merge-mechanism-agnostic, performing no merge-hook discovery or arming and depending on no scanner (`scanMods`) lookup. The delivery mechanism is evaluated when acted on, not at consume: the existing `merge guard` discovers the registered hook and arms `mod-block: merge:{hook}` at delivery time, and with no registration its shipped hookless/manual-local instruction path covers the route unchanged (`merge guard` is already "the same under both merge: policies" and already names "the manual merge when no registration exists" — `skills/first-officer/references/fo-merge-core.md`). The ceremony trigger hangs off the gate consumption (a pending terminal-target application), not off the stage — stage-keyed triggering is exactly what made the spending moment ambiguous. Non-terminal consumes are unchanged (`pending→consumed` + status advance, as today, `internal/gates/application.go:165-181`). There is no class that consumes before delivery: under `merge: pr`, registered `merge: local`, and manual local merge with no registration, the terminal approval follows this same transaction.
2. **`merge guard` is the sole terminal consumer.** No other writer may spend a terminal-target approval or write terminal status on an entity carrying one (the one producer-side refusal this requires is argued in "One guard the transaction proves necessary" below).
3. **Delivery success is one atomic envelope.** With delivery proven — merge sentinel `pr-merge:{N}` under `merge: pr`, the registered local hook's completion under `merge: local`, or the captain-mandated manual local merge — `merge guard --verdict <v>` writes, in ONE full-document replacement: `application.state: pending→consumed` (exactly-once via the existing `validateApplicationMutation` guard), `status := <terminal>`, `verdict := <v>`, `completed := <stamp>`; then merge guard's existing archive/commit/publish (`internal/status/merge.go`). Mechanism honesty: the four-field application/status/verdict/completed write is a **necessary NEW composition, not an existing helper** — today's `writeDocumentAndStatus` replaces only `gates`+`status` (`internal/gates/application.go:281-283`; full-document swap `internal/gates/io.go:188-226`), and today's merge finalization writes status/verdict/completed *separately* via `runSet` (`internal/status/merge.go:392-399,702-709`). The envelope generalizes the proven gates-writer full-document replacement to carry all four fields through the same guarded mutation, and when introduced it must **preserve merge guard's current status validations** (the mod-block/sentinel/verdict checks today's finalization performs before writing) — moved into the envelope, not dropped. `application.state: pending→consumed` (exactly-once via the existing `validateApplicationMutation` guard), `status := <terminal>`, `verdict := <v>`, `completed := <stamp>`; then merge guard's existing archive/commit/publish (`internal/status/merge.go`). The authorization is spent at exactly the moment delivery proof is in hand, and the fields that used to desync (status vs verdict/completed) are written in the same swap by the same writer in every delivery class — done-but-undelivered becomes unrepresentable.
4. **Delivery failure requiring rework writes the existing unspent semantic.** The same ceremony, told the delivery requires rework — `merge guard --rework` (one bounded outcome flag; no `--to`, no `--by`, no `--pr`). The name matters: `--failed` reads as transient delivery trouble (CI red, push failure), which spends nothing and takes no flag (point 5); `--rework` names the irreversible action — supersede this approval and route through the declared `feedback-to`: one guarded replacement writing `application.state: pending→superseded` (the drift path already makes exactly this write through the same guarded mutation, `internal/gates/application.go:155-165`), `status :=` the record stage's **declared `feedback-to`**: the target *lookup* is existing and proven (`applicationForDecision`, `internal/gates/operation.go:486-506`), with `mod-block` and `pr` cleared. Today's routing, however, silently falls back to the same stage when `feedback-to` is missing (`internal/gates/operation.go:505-510`) and parsing never validates that the target is defined/nonterminal (`operation.go:552-570`) — so the `--rework` refusals below (missing/undefined/terminal target) are **necessary NEW validation around the proven lookup, not unchanged shipping semantics**. `superseded` already means the application will not be spent (durable ruling) — no new state, no subtree, no journal, no caller-supplied actor string. Normal lifecycle resumes from the routed stage; re-entry into the gated stage appends a successor attempt on the same gate record through the existing prepare path; the frozen superseded attempt is history, never rewound.
5. **Retryable delivery trouble changes nothing.** Push failure, CI timeout, host error: the approval stays pending and the delivery step is retried. `merge guard` without delivery proof writes nothing and reports armed/blocked (its current behavior). This is durable ruling :17 as shipped prose: only the authorization is exactly-once; the delivery effect is at-least-once retryable, and receipts stay declined. A repeated `gate consume` on the same still-pending terminal application is idempotent re-routing (the same `approved-awaiting-merge` route is returned again) — the routing is a delivery effect, so at-least-once applies; the authority does not move.
6. **Nothing else.** The application state enum stays `pending/consumed/superseded/not-applicable` (`internal/gates/model.go:303-305`); the mutation guard stays the byte-exact parameterized from/to swap; the entity lock stays as shipped; `scanMods` is untouched (see Out of scope).

### Re-consumability: why staying pending is safe without a new state

Consume eligibility is `pending` ∧ `status == record.Stage` — which the routed entity still satisfies, so the transaction deliberately accepts a second `gate consume`: routing is the at-least-once effect (:17) and re-consuming an already-routed entity is a no-op (nothing to arm at consume). The authority itself moves exactly once, in `merge guard`, through the existing pending-consume guard; a `superseded` application is refused by the same eligibility check that refuses every non-pending state. The rejected design bought this property with a new `delivering` enum value; the minimal transaction gets it from the spend's own exactly-once guard.

### One guard the transaction proves necessary

Point 2 ("sole terminal consumer") is false while a producer stays open: today's non-forced `status --set status=<terminal>` can enter terminal status directly while a terminal-target application is pending, recreating done-but-undelivered by hand (this was staff-review finding 15 in cycle 1). The minimal countermeasure, argued from the transaction, not from safety-padding: a non-forced `status --set` whose result is terminal status is refused **while the entity carries a pending terminal-target application**, naming `merge guard` as the writer; `--force` remains the uniform escape hatch every existing guard honors. Refusal-only predicate on an existing code path; no state, no record, no scan changes.

Read first per the revise assignment (`docs/roadmap/durable-decisions/index.md`):

- **:13 — the unreleased-v1 recorder has no compatibility or migration path.** No adoption shape test, no legacy finalize/regress route, no migration. The one live entity cited in the rejection (`fo-boot-install-hint-linux-direct-sandbox`) has since been archived (`state: archive fo-boot-install-hint-linux-direct-sandbox (merge guard)`) and is history, not a design input. Any entity still in the legacy shape is outside this design's write paths; it is handled by direct captain action, not shipped semantics.
- **:17 — only the authorization is exactly-once; the dispatch effect is at-least-once retryable; receipts stay declined.** The spend (`pending→consumed`) happens exactly once, atomically with delivery proof, through the existing guarded mutation. Consume-side routing and delivery retries are declared at-least-once effects with no delivery journal, no effect receipts, no reversal record — the authorization record is never repurposed as a delivery ledger.
- **`superseded` already means the application will not be spent.** The failure path writes the existing `pending→superseded` transition and nothing more; no new state duplicates its meaning.

### Alternatives considered

1. **The cycle-1 architecture** (delivering/reversed/reversal journal, scanner rewrite, shared flock, legacy adoption, `--to`/`--by`). Rejected by the captain at the ideation gate; retained below only as history.
