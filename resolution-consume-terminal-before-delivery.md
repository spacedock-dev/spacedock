A gate approval on a terminal-target stage (`validation → done`) is *immediately consumable into terminal status*: the binding approval's authority is marked spent (`consumed=true`) and the entity's status flips to `done` at consume time, while delivery (PR push, CI, merge) and workflow terminal fields (`verdict`, `completed`) remain pending. Three desyncs follow:

1. **Authority is spent before the spend is justified.** The consumed approval is irrevocable by design ("never double-applied"), yet the deliverable it ratified is only *pending* — there is no delivery proof at the moment the approval is spent.
2. **Two status classes per entity.** `status=done` (decision monoid) with empty `verdict`/`completed`/`pr` (delivery incomplete). The mod-block guard withholds terminal fields deliberately, but the status field itself already claims terminal. CL feedback: "right now if it's done it can't be sent back."
3. **No regression verb exists.** If the PR fails (CI red, closed-unmerged, a new defect uncovered), the workflow's own pre-done `feedback-to: implementation` wiring is *inert* (it's scoped to pre-done rejections). The pr-merge mod's answer to a closed PR is literally "report to the captain and wait"; the only physical reverse routes are frontmatter surgery or a second gate cycle that would have to dance around the consumed record. Prior live precedent (`worktree-clear-guard-misfire-on-backward-route`) shows even bookkeeping of a backward route trips the same merge-hook guard.

The pure-`merge: local` workflow hides this; any PR-gated workflow exposes it. Three review rounds missed it because they scoped to the API of gates, not the failure mode of delivery-after-consume.

## Problem

The consumption semantic treats "terminal-stage approval" and "terminal delivery" as one event; they are two, and the second can fail. Concretely, today:

1. **One atomic write, one irreversible spend.** `gates.Consume` (`internal/gates/application.go`) co-writes `application.state: consumed` and `status: done` in a single entity replacement for a terminal-target approval. The authority ledger and the workflow status both claim completion at the same instant, while the pr-merge mod deliberately withholds `verdict`/`completed` behind the merge-hook guard. Authority is spent with zero delivery proof in hand.
2. **Two status classes, one field.** A `status=done` entity is either *delivered* (verdict/completed set, archived or archivable) or *done-but-undelivered* (PR open/unpushed/CI unknown). Nothing in frontmatter distinguishes them without composing status + mod-block + pr + verdict — and CL's operational rule is "if it's done it can't be sent back," so the second class is a dead end.
3. **No recorded reverse route.** `applicationForDecision` wires `revise` to `feedback-to` only for pre-done gate rejections. The application's durable state enum (`pending/consumed/superseded/not-applicable` in `model.go::validateApplication`) has no value for "delivery failed after approval," `ValidateTransition` freezes closed attempts, and the only physical routes backward are frontmatter surgery or a second gate cycle that must dance around the consumed record (both rejected in the filing). The pr-merge mod's CLOSED-PR answer — "report to the captain and wait" — has no verb behind it.

The pure-`merge: local` workflow hides the hole (delivery is local and synchronous inside the terminal ceremony, so the window between spend and proof is small). Any PR-gated workflow exposes it. The model must make approval-authority, stage status, and terminal fields cohere in BOTH directions of the consume/delivery boundary: forward (spend lands only with delivery proof) and backward (a failed delivery is a recorded state transition, never surgery or re-bought authority).

## Proposed approach

**Pending-preserving consume; `merge guard` as the sole terminal consumer; the existing `pending→superseded` as the send-back.** One rule for every terminal approval regardless of merge policy or hook registration: `gate consume` never spends a terminal-target approval and never writes terminal status. This is the captain's six-point minimum (his revise resolution, cycle 1 below) taken as the whole design. Nothing is added beyond the six points except one refusal the transaction itself requires (argued below); no `delivering`, no `reversed`/`reversal`, no `--to`, no actor flag, no compatibility path, no scanner rewrite, no lock work.

### The minimal transaction (the entire mechanism)

1. **Consume routes, does not spend.** `gate consume` on an approval whose target stage is terminal leaves `application.state: pending`, leaves `status` at the gated stage, and routes the entity into the terminal merge ceremony: when a merge hook is registered it arms `mod-block: merge:{hook}` in the consume write; with no registration it reports the routing and the FO drives delivery by hand (`merge guard` is already "the same under both merge: policies" and already names "the manual merge when no registration exists" — `skills/first-officer/references/fo-merge-core.md`). The ceremony trigger hangs off the gate consumption (a pending terminal-target application), not off the stage — stage-keyed arming is exactly what made the spending moment ambiguous. Non-terminal consumes are unchanged (`pending→consumed` + status advance, as today, `internal/gates/application.go:165-181`). There is no class that consumes before delivery: under `merge: pr`, registered `merge: local`, and manual local merge with no registration, the terminal approval follows this same transaction.
2. **`merge guard` is the sole terminal consumer.** No other writer may spend a terminal-target approval or write terminal status on an entity carrying one (the one producer-side refusal this requires is argued in "One guard the transaction proves necessary" below).
3. **Delivery success is one atomic envelope.** With delivery proven — merge sentinel `pr-merge:{N}` under `merge: pr`, the registered local hook's completion under `merge: local`, or the captain-mandated manual local merge — `merge guard --verdict <v>` writes, in the single full-document replacement the gates writer already performs (`writeDocumentAndStatus`, `internal/gates/application.go:281`): `application.state: pending→consumed` (exactly-once via the existing `validateApplicationMutation` guard), `status := <terminal>`, `verdict := <v>`, `completed := <stamp>`; then merge guard's existing archive/commit/publish (`internal/status/merge.go`). The authorization is spent at exactly the moment delivery proof is in hand, and the fields that used to desync (status vs verdict/completed) are written in the same swap by the same writer in every delivery class — done-but-undelivered becomes unrepresentable.
4. **Delivery failure requiring rework writes the existing unspent semantic.** The same ceremony, told the delivery failed — `merge guard --failed` (one bounded outcome flag; no `--to`, no `--by`, no `--pr`): one guarded replacement writing `application.state: pending→superseded` (the drift path already makes exactly this write through the same guarded mutation, `internal/gates/application.go:155-165`), `status :=` the record stage's **declared `feedback-to`** resolved through the existing revise-decision routing (`applicationForDecision`, `internal/gates/operation.go:486-506`), with `mod-block` and `pr` cleared. `superseded` already means the application will not be spent (durable ruling) — no new state, no subtree, no journal, no caller-supplied actor string. Normal lifecycle resumes from the routed stage; re-entry into the gated stage appends a successor attempt on the same gate record through the existing prepare path; the frozen superseded attempt is history, never rewound.
5. **Retryable delivery trouble changes nothing.** Push failure, CI timeout, host error: the approval stays pending and the delivery step is retried. `merge guard` without delivery proof writes nothing and reports armed/blocked (its current behavior). This is durable ruling :17 as shipped prose: only the authorization is exactly-once; the delivery effect is at-least-once retryable, and receipts stay declined. A repeated `gate consume` on the same still-pending terminal application is idempotent re-routing (arm already present) — the routing is a delivery effect, so at-least-once applies; the authority does not move.
6. **Nothing else.** The application state enum stays `pending/consumed/superseded/not-applicable` (`internal/gates/model.go:303-305`); the mutation guard stays the byte-exact parameterized from/to swap; the entity lock stays as shipped; `scanMods` is untouched (see Out of scope).

### Re-consumability: why staying pending is safe without a new state

Consume eligibility is `pending` ∧ `status == record.Stage` — which the routed entity still satisfies, so the transaction deliberately accepts a second `gate consume`: routing is the at-least-once effect (:17) and re-arming is a no-op. The authority itself moves exactly once, in `merge guard`, through the existing pending-consume guard; a `superseded` application is refused by the same eligibility check that refuses every non-pending state. The rejected design bought this property with a new `delivering` enum value; the minimal transaction gets it from the spend's own exactly-once guard.

### One guard the transaction proves necessary

Point 2 ("sole terminal consumer") is false while a producer stays open: today's non-forced `status --set status=<terminal>` can enter terminal status directly while a terminal-target application is pending, recreating done-but-undelivered by hand (this was staff-review finding 15 in cycle 1). The minimal countermeasure, argued from the transaction, not from safety-padding: a non-forced `status --set` whose result is terminal status is refused **while the entity carries a pending terminal-target application**, naming `merge guard` as the writer; `--force` remains the uniform escape hatch every existing guard honors. Refusal-only predicate on an existing code path; no state, no record, no scan changes.

### Durable rulings touched, and how each is honored

Read first per the revise assignment (`docs/roadmap/durable-decisions/index.md`):

- **:13 — the unreleased-v1 recorder has no compatibility or migration path.** No adoption shape test, no legacy finalize/regress route, no migration. The one live entity cited in the rejection (`fo-boot-install-hint-linux-direct-sandbox`) has since been archived (`state: archive fo-boot-install-hint-linux-direct-sandbox (merge guard)`) and is history, not a design input. Any entity still in the legacy shape is outside this design's write paths; it is handled by direct captain action, not shipped semantics.
- **:17 — only the authorization is exactly-once; the dispatch effect is at-least-once retryable; receipts stay declined.** The spend (`pending→consumed`) happens exactly once, atomically with delivery proof, through the existing guarded mutation. Consume-side routing and delivery retries are declared at-least-once effects with no delivery journal, no effect receipts, no reversal record — the authorization record is never repurposed as a delivery ledger.
- **`superseded` already means the application will not be spent.** The failure path writes the existing `pending→superseded` transition and nothing more; no new state duplicates its meaning.
- **Terminal delivery runs under both policies and manual local merge (fo-merge-core).** `merge guard` is already the single terminal ceremony across those classes; making it the sole consumer closes the hole uniformly with no carve-out class — the rejected design's hookless exemption was the defect, and this design has none.

### Boundary coherence (one table, both directions, all delivery classes)

| boundary event | authority (`application.state`) | status | delivery/terminal fields |
|---|---|---|---|
| consume, non-terminal target | `pending→consumed` | → target | as today |
| consume, terminal target (any policy, with or without registration) | `pending` (unchanged) | unchanged | ceremony armed: `mod-block: merge:{hook}` when a hook is registered |
| repeated consume on the pending terminal application | `pending` (unchanged) | unchanged | idempotent re-routing; no authority movement |
| `merge guard`, delivery proven | `pending→consumed` | → terminal | `verdict` + `completed` in the same replacement; mod-block/pr retire with the envelope |
| `merge guard --failed` (delivery requires rework) | `pending→superseded` | → declared `feedback-to` | `mod-block`/`pr` cleared; verdict/completed untouched (never written pre-delivery) |
| `merge guard`, delivery not yet proven (retryable trouble) | `pending` (unchanged) | unchanged | unchanged; reports armed/blocked |
| non-forced `status --set` to terminal while a terminal-target application is pending | unchanged | refused | refused, naming `merge guard` |

### Alternatives considered

1. **The cycle-1 architecture** (delivering/reversed/reversal journal, scanner rewrite, shared flock, legacy adoption, `--to`/`--by`). Rejected by the captain at the ideation gate; retained below only as history. Restated here solely to name why its pieces stay out: `superseded` already carries unspent, the authorization record is not a delivery journal (:17), legacy adoption violates :13, and hook-keyed classes recreate the hole.
2. **Consume writes nothing at all on terminal targets (no arm).** Rejected: the ceremony needs its activation event at consume (point 1); with no routing signal the pr-merge mod has no trigger and the FO gets no recorded indication of what is owed.
3. **Status advances to terminal at consume with the application pending.** Rejected: it keeps the two-classes-of-done defect in a new key; the problem's invariant requires all terminal writes in the delivery envelope (point 3).
4. **Overloading `--verdict rejected` for the delivery-failure send-back.** Rejected: `rejected` is a terminal outcome (the deliverable is refused); delivery-failure-rework is a routing outcome. Conflating them either strands mid-pipeline entities in terminal status or erases a real terminal verdict.

## Out of scope

PR body creation mechanics of the pr-merge hook; CI-check polling mechanics (how a delivery failure is *discovered* is unchanged — only its route is new); non-terminal consume behavior; entities without gate records; workflow stage grammar. Specifically unchanged, each with its reason: `scanMods` — the consume-time registration lookup only decides ceremony arming (armed mod-block vs manual instruction); a mis-scan degrades routing cosmetics, never authority, because no scanner-dependent branch writes the authorization (the spend path is scan-independent, keyed on the pending application) — so the cycle-1 scanner rewrite is unnecessary (stated as the explicit proof point 6 requires); the entity lock/CAS — all writes in the transaction reuse the existing gates-writer full-document replacement; legacy/compatibility handling for the done-but-undelivered shape — durable ruling :13; dispatch selectors — the routed entity stays at its gated stage, which dispatch never selects as stage work.

## Acceptance criteria

**AC-1 — A terminal approval whose delivery fails after the gate's approval round-trips through rework to true-done entirely inside the workflow's own verbs: spend happens only with delivery proof, the send-back is recorded as the existing supersede through the declared feedback-to, and re-entry needs no surgery and no second gate cycle.** *(value-measuring: exercises the incident scenario end to end)*
Verified by `internal/cli/terminal_consume_test.go::TestTerminalDeliveryFailureReworkRoundTrip` — a CLI-driven fixture starting from a real recorded approval: README workflow with a registered pr-merge hook; binding approval recorded; CLI `gate consume` → asserts `application.state=pending`, `status` unchanged at validation, `mod-block=merge:pr-merge` armed. Delivery fails (PR reported closed-unmerged): `merge guard --failed` → asserts `status=implementation` (the declared `feedback-to`), `application.state=superseded`, `mod-block`/`pr` cleared, `gates.current` unchanged. Rework, re-enter: successor gate attempt-2 on the same record, fresh approval, consume (pending again), delivery proven (merge sentinel `pr-merge:{N}`), `merge guard --verdict passed` → asserts `status=done` + `verdict=passed` + `completed` set + `application.state=consumed`, all four in one replacement. Independently movable baseline: the same fixture against the pre-change binary reproduces today's hole (consume flips straight to `done` + `consumed` with zero delivery proof; no `--failed` route exists); any variant whose success envelope splits status from verdict/completed, or whose failure route leaves `pr`/`mod-block` set or the application pending, moves the assertions the wrong way.

**AC-2 — The sole-consumer invariant: on every delivery class (`merge: pr`, registered `merge: local`, manual local merge with no registration), terminal status and the authorization spend occur only inside merge guard's delivery envelope, and `status==terminal ⟺ verdict≠"" ∧ completed≠"" ∧ application consumed` holds for every entity reachable through it.**
Verified by `internal/cli/terminal_consume_test.go::TestTerminalSpendOnlyInDeliveryEnvelope` — for each delivery class, consume leaves `pending` + status unchanged, and the only terminal entry is the merge guard envelope; plus refusal cases: non-forced `--set status=done` while the terminal application is pending is refused naming `merge guard` (`--force` still overrides), and `gate consume` run twice performs idempotent routing with no second spend. Adversarial discriminator: leaving today's always-consume branch intact, or allowing any non-forced terminal `--set` past the pending application, turns the matrix red.

**AC-3 — Retryable delivery trouble spends nothing, routes nothing, and loses nothing.** Verified by `internal/cli/terminal_consume_test.go::TestTerminalRetryLeavesAuthorityPending` — merge guard invoked before delivery proof (no sentinel, PR open) writes no authority, status, or terminal-field change and reports waiting; after the retryable failure clears, the success envelope lands exactly once, and a re-invoked `merge guard --verdict passed` after `consumed` is handled by the existing guards (no double write, clean refusal/no-op).

Supporting (mechanism) criteria, subordinate to AC-1..3:
- `internal/gates/*_test.go`: terminal-target consume preserves pending and arms; non-terminal consume unchanged; `merge guard`'s spend reuses `validateApplicationMutation("pending","consumed")`; the `--failed` write reuses `("pending","superseded")`; a superseded application remains non-eligible (fail-closed, as today).
- `--failed` refusal matrix (`internal/cli`): refuses with no pending terminal-target application; refuses when the record stage declares no `feedback-to` or a terminal/undefined one (same misconfiguration rule the existing revise routing applies — no silent fallback); asserts the cleared `mod-block`/`pr` and unchanged `gates.current`.
- Golden status fixture: the routed entity (pending terminal application, status unchanged) surfaces through the existing pending-application display; no new readiness states are introduced.
- Regression pinning: existing `merge_guard_test.go` fixtures for archived/hookless-finalize paths stay green or are deliberately re-based with the diff named in the implementation report.
