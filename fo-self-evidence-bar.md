## Problem
The FO operating contract (`skills/first-officer/references/first-officer-shared-core.md`, `## Working Principles`) enforces "prefer a code gate over a prose-only rule" and the gate AC cross-check on the ENSIGN's deliverable and the gate review. It does not bind the FO's OWN dispatcher decisions to the same evidence bar. Two real failures followed (ezf/hf, 2026-06-16): (1) the FO judged `claude-live` "unrelated" to a change in `claude-fo-dispatch.md` and merged without it; (2) the FO classified a live-CI red as "the known flake" by inheriting a handoff label instead of reading this run's failing test. Both are FO-side judgment calls the contract leaves unconstrained, so the discipline is self-exempting exactly where it matters.

## Approach

Three surfaces, composed. The FO contract already binds "prefer a code gate over a prose-only rule" and the AC cross-check to the ENSIGN's deliverable and the gate review; this adds the same bar to the FO's OWN dispatcher decisions, host-neutrally, and slims the dev-workflow README to inherit it.

### S1 — runtime-neutral Working Principle (`skills/first-officer/references/first-officer-shared-core.md`, `## Working Principles`)

A new bullet, host-agnostic (no `claude-live`/`codex-live` literals). Proposed text (tight — the leanness ceiling is shared with zm/vcm, see Composition cross-check):

> **Hold your own gate, merge, and triage calls to the bar you impose on workers.** The proof discipline above binds not just the ensign's deliverable and the gate review but the FO's own dispatcher decisions:
> - **Required verification follows from what changed, not the FO's sense of relevance.** A check the change exercises is not waived as "unrelated" by intuition; a relevant check that flakes is re-run to green (serial, isolated), never skipped. "It's unrelated" is a claim the change must substantiate, not a dispatcher judgment.
> - **A result is "green" only when the relevant check actually ran and passed.** An unapproved, skipped, or cancelled check is not a pass; the absence of a red is not the presence of a green.
> - **A failure is read from this run's evidence** — the failing test, assertion, or error in front of you. A prior session's or a handoff's label ("the known flake") is a hypothesis to confirm against this run, not a verdict to apply.
> Where the captain holds the gate, this bar relocates to the evidence the FO surfaces there — see `present-gate`.

### S2 — `present-gate` evidence rule (`skills/present-gate/SKILL.md`, assembly rules)

A new assembly rule (the interactive manifestation — the more dangerous case, because a mis-framed gate makes the human ratify the FO's error without ever seeing the evidence):

> N. **Surface verification state as evidence, not as a label.** When the gate turns on checks that ran outside this presentation (CI lanes, a validation report), state which relevant checks actually ran and passed — an unapproved/skipped/cancelled check is named as not-a-pass, not folded into "PASSED" — and read any failure from this run's evidence (the failing test/assertion), never from an inherited "known flake" label. The captain votes on which checks are green and why a red is red.

### S3 — dev-workflow README inherits (`docs/dev/README.md`, Proof policy `path→lane` bullet)

The generic statement (relevance-not-relatedness, green-means-ran-and-passed, read-this-run's-failure) now lives ONCE in S1. The README bullet slims to the dev-specific realization and references the generic principle instead of re-deriving it: keep the path→lane mapping (Claude adapter→`claude-live`; a host adapter→that host's lane; the host-neutral dispatch core or shipped contract `skills/**/references/**`→every host lane) and the merge rule (a relevant lane is REQUIRED green; a flake is re-run to green, never skipped/left-unapproved/waved-off); drop the independently-restated "read this run's failing test, not the inherited label" clause, which S1 now owns. Net effect: no duplication of the generic clause across the two files.

### Both modes — autonomous AND gate judgment (preserved)

- **Autonomous / given-the-conn:** the FO is the decider; S1 binds the merge/gate/triage decision directly. Proven by AC-1.
- **Interactive gate judgment:** the captain decides, but on the FO's PRESENTATION; S2 relocates the bar to the evidence the FO surfaces, so a mis-framed "PASSED / lane unrelated / known flake" gate cannot make the human ratify an unseen error. Proven by AC-3.

## Spike / proof determination (resolves the former "Notes for ideation")

The open question was: what genuinely proves a behavioral FO principle, given that a contractlint "the phrase is present" check is the prose-grep tautology this very policy bans? **Resolved as a composition, not a single check:**

- **The value proof is the live merge/triage scenario (AC-1), not a prose check.** A behavior change can only be proven by observing the behavior; this is the smallest sufficient mechanism for a behavioral claim.
- **The runtime-neutrality property IS code-gateable (AC-2)** via structural absence — so the entity that preaches "prefer a code gate" ships a code gate for the part that can be gated, and reserves the live drive for the part that genuinely cannot.
- **The binary diff→lane merge gate is rejected as this entity's proof** (Out of scope) — no binary knows the mapping, and building one over-climbs zm's mechanism gate.

**No new mechanism spike needed.** The riskiest path — "can the live-scenario apparatus drive an FO to a MERGE/TRIAGE decision and assert a durable refusal?" — is already proven by the existing `merge-hook-guardrail` scenario (it drives the FO to terminalization and asserts the guard refuses bypass) plus the four-step add-a-scenario recipe (which MANDATES an offline negative proving the assertion catches the broken end-state).
