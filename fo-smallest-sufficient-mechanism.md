## Problem

The FO contract carries a "simplest approach" principle, but a principle is rationalizable — so the FO climbs to a heavier mechanism (workflow, dispatched worker, PR) where a direct in-house edit / direct commit / no-action is correct. Observed escape hatches:

- **Ultracode → orchestrate-everything.** "Use Workflow by default on substantive tasks" got read as "spin a workflow for everything," overriding the simplest-thing discipline — a dynamic workflow plus a dispatched worker to apply edits to ~7 entity files whose verbatim content the FO already held.
- **Dispatcher literalism.** "Never do stage work" became "never touch a file," so FO shaping-edits (writing ACs into entities) were offloaded to a worker instead of done in-house with Edit.
- **PR over-generalization.** The team's contract/code direct-to-main→PR move was applied to strategy prose; a roadmap doc the convention commits directly (0221 precedent: `index.md` + `dispatch-sprint-execution.md` committed direct, never PR'd) got a PR with CI lanes.

## Approach — convert the principle into a forcing function

1. **Smallest-sufficient-mechanism gate, ranked ABOVE Ultracode.** Before any workflow, dispatched worker, or PR, the FO states in one line why the rung below cannot do it. Ladder: do-nothing → in-house Read/Edit → one worker → workflow; and direct-commit → PR. Climbing is justified ONLY by genuine fan-out (many independent units), required isolation (parallel mutation that would collide), or independent adversarial verification — NEVER by "it's substantive," "Ultracode is on," or "I'm the dispatcher so I don't touch files." The gate binds the OTHER direction too: before re-running verification a stage already owns, the FO states why the validator's report plus a cheap spot-check is insufficient — redundant re-verification is justified ONLY when the report shows the required check did not actually run green (the z25 read: an unapproved/skipped/red lane is not a pass), never as a reflexive "double-check."
   - **Scope: discretionary climb, not commissioned dispatch.** The gate governs the FO's DISCRETIONARY choice of mechanism for an ad-hoc task — the ezf incident: choosing a workflow + worker to apply ~7 edits it could Edit in-house. It does NOT re-gate the normal dispatch of a COMMISSIONED workflow stage that already declares a worker: k74g's `«engage»` loop dispatching ready entities via `«dispatch.next-action»()` is executing an already-declared mechanism, so its justification is STANDING (made when the workflow was commissioned), not re-narrated per entity. The gate fires on a discretionary climb; it never turns "fire and walk away" engage into per-entity justification narration.
2. **Scope Ultracode.** It raises the thoroughness/coverage of the ANSWER, not the weight of the MECHANISM. A direct in-house multi-file Edit IS the exhaustive-correct answer.
3. **Named busywork the FO refuses (both directions of the ladder):** PRs/CI for convention-direct prose (roadmap/state docs commit directly); dispatching deterministic edits whose content the FO already holds; workflows with no fan-out / isolation / verification need; re-formalizing work already done; **gate-time re-verification** — re-running stage-owned validation (a worktree + `go build` + a full `go test ./...`) inline at gate time to "double-check" a fresh validation stage whose report already covers it, instead of reading the validator's report and doing a cheap spot-check that the reported check actually ran green. The first four are over-orchestration (climbing ABOVE the smallest rung); the last is redundant re-verification (re-doing work a stage already owns) — the same one-line justification is owed before EITHER. This is the friction-#1 fold: the FO must not climb OR re-do; smallest-sufficient is a floor and a ceiling.
4. **Binds ALL FO action**, not just entity-stage tasks — release machinery and sprint shaping are not framing escape hatches from the gate. "ALL FO action" means every DISCRETIONARY mechanism choice (release machinery and sprint shaping included — no domain is exempt); it does NOT re-gate a commissioned stage's already-declared dispatch (the scope clause in point 1). A commissioned workflow's declared dispatch is standing justification, not a per-entity climb — that is not an escape hatch, it is the gate correctly not firing.
