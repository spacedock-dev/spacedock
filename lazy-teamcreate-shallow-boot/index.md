Make the first officer cheap to boot and reach interactive readiness fast. Boot forensics on a live FO session (`docs/roadmap/0203-fo-efficiency/boot-analysis.md`) measured **~160k peak context and ~13.6 min wall-clock to reach an interactive greet — with no team created and no worker dispatched.** A 100% pre-dispatch session paid full deep-boot cost. The FO front-loads its entire contract (both reference files ~16.2k), the full workflow README (~8.1k), both mod files (~6.5k), and renders the human status table (twice, ~8.7k) — then thinks at 100k+ context, where the two slowest turns (128.6s, 100.1s) fired. None of that was needed to greet the captain.

This is the **backbone of the 0.20.3 "FO efficiency" milestone** (`docs/roadmap/0203-fo-efficiency/README.md`). It is ONE task, THREE sequential phases: P1 contract structural split → P2 lazy-TeamCreate → P3 shallow-boot-then-greet. The ideation is consolidated from two completed static-analysis spikes (`T1-ideation.md` = Phase 1, verdict VIABLE; `j9-phases-2-3-ideation.md` = Phases 2-3, verdict VIABLE).

## Problem

- **Time-to-interactive is gated on the full deep-boot, not a fast orient pass.** Generation latency scales with loaded context, so the wall-clock is dominated by thinking at 100k+ — most of it over material the greet never uses.
- **TeamCreate's ~89k cache-creation is on the critical path before the dispatch gate.** Creating a Claude team re-caches the whole conversation prefix under the new team context. The milestone's Cost-levers table ranks this as the single biggest lever (~89k removed) — far larger than the contract reads (~16k), the status-table render (~8.7k), or the mod reads (~6.5k). The measured session never created a team because it never dispatched, so the entire ~89k is avoidable on a no-dispatch boot — *if* the contract stops telling the FO to create a team at startup.
- **The contract is read whole, up front, before any work begins.** ~70% of the Claude runtime adapter is team/dispatch material a no-dispatch boot never uses, yet it loads first (forensics rows 2-3, t=8-9s).

## Cost levers (why this task is the backbone)

| Lever | ~boot cost removed | Needs the contract split? |
|-------|-------------------:|---------------------------|
| Lazy-TeamCreate (defer the team-mode prefix re-cache) | **~89k cache-creation** | no (Phase 2) |
| Defer contract reads at greet | ~16k | yes — minimal (Phase 1) |
| Defer the human status-table render | ~8.7k | no (Phase 3) |
| Defer mod-file reads | ~6.5k | no (Phase 3) |
| README frontmatter-only read (defer the body) | ~7.7k | no (Phase 3) |

The ~89k lazy-TeamCreate dwarfs the rest and sits on the critical path *before the dispatch gate*. The contract split (Phase 1) is the enabling refactor for the one lever that needs it, and doubles as the "audit and clean up the FO contract" ask.

## Proposed approach

Three sequential phases. Each is behavior-preserving where it moves content; the *new* behavior (greet-first sequencing) is Phase 3 and rests on Phase 1's split.

### Phase 3 — shallow-boot-then-greet (greet off `status --boot --json`)

Reshape the Startup procedure so the FO reaches the greet through exactly the before-greet step set, then stops for input. The new shallow-boot sequence:

```
contract-gate (S1: version mismatch aborts before any state read)
  → git root (S2)
  → workflow discovery (S3)
  → README FRONTMATTER read (S4-slim: entity-label, stage names/ordering, gate/terminal flags)
  → status --boot --json (S5: state-summary source — orphans, pr_state w/ LIVE merge state, dispatchable, team_state, state_backend)
  → split-root halt-gate (S6: prevents a false-empty greet off an uninitialized checkout)
  → split-root pull-on-boot (S7: state freshness; rebase-conflict HALT)
  → merged-PR sweep (S7b: for each pr_state entry state==MERGED & non-terminal, read
       _mods/pr-merge.md + run its startup-hook advancement; no-op + no mod read when none merged)
  → GREET the captain (state summary off the boot JSON, including any S7b-advanced entities;
       able to present a gate) and STOP for input
```

The before-greet step set splits into two cost classes: (i) **boot-resident READS** — contract gate, git root, discovery, README frontmatter, `status --boot --json`, split-root halt/pull — none of which read a mod file or create a team; and (ii) the **one cheap correctness-relevant ACTION**, S7b's merged-PR advancement, which reads `_mods/pr-merge.md` ONLY when the boot JSON shows an actually-merged PR. The expensive deferrals — TeamCreate, the dispatch/merge reference modules, the comm-officer spawn, the README body, the human status-table render — all stay past the greet. "Cheap correctness-relevant action before-greet; expensive reads + TeamCreate deferred" is the dividing line.

- **Greet off the boot JSON.** The FO greets with a state summary built from `status --boot --json` (orphans, pr_state, dispatchable, team_state, state_backend) and the README frontmatter (entity-label, stage taxonomy, gate flags), then stops. It can present a gate from this state without a team (gates are captain-facing text, not team messages).
- **README frontmatter-only read (S4-slim).** Startup step 4 reads the README frontmatter (~175 tokens: entity-label, stage names/ordering, gate/terminal flags) and defers the ~7.7k body (per-stage prose, proof policy, templates, CI docs) to the phase that consumes it. The boot JSON cannot substitute for the frontmatter — confirmed in `internal/status/json_commands.go`: the boot envelope carries NO `"stages"`/`"labels"`/`"gates"` key, so the frontmatter read stays before-greet; only the body defers.
- **Defer mod-file reads (with an explicit greet-time trigger for the pr-merge advancement ACTION).** The comm-officer mod FILE defers to first dispatch (its spawn needs a live team). The pr-merge mod FILE's `## Hook: startup` ADVANCEMENT, however, does NOT defer past the greet — see M3 below: it fires at an explicit **greet-time / first-action trigger** (after the boot JSON read and the split-root pull, immediately before or as the FO composes the greet), because it is a cheap, correctness-relevant action (`gh pr view` + status mutations + archive + worktree removal) that a greet-and-stop boot would otherwise never run. The greet learns *which* mods are registered from the boot JSON `mods` map and reports PR/mod/orphan state off the boot JSON; the only mod file it reads before greeting is `_mods/pr-merge.md` (and only when the boot JSON shows a PR-bearing non-terminal entity whose `pr_state` entry is `MERGED` — i.e., there is actually a merge to advance).

  **Greet-time trigger, stated explicitly (closes M3).** Reshape the boot sequence so a merged-PR advancement runs before-greet:
  ```
  ... → status --boot --json (S5) → split-root halt/pull (S6/S7)
    → MERGED-PR SWEEP (S7b): for each pr_state entry whose state == "MERGED" and whose
        entity status is non-terminal, read _mods/pr-merge.md and run its startup-hook
        advancement (mod-block= clear → terminalize verdict=PASSED → archive → worktree
        remove); skip entirely when no such entry exists (the common boot — no mod read)
    → GREET (reports any just-advanced entities) and STOP
  ```
  This is the one mod-file read that is correctness-bound to the greet. It is bounded by the boot JSON (the FO already knows from `pr_state` whether any entry is `MERGED`, so on the overwhelmingly common boot with nothing merged it reads zero mod files and pays nothing). comm-officer spawn and the merge-hook merge action stay deferred — neither is correctness-relevant to a greet-and-stop boot (no team to spawn into; no entity at the terminal merge boundary).
- **Defer the human status-table render.** The FO never renders the human-formatted table for its own reasoning (it has the boot JSON); it renders it to the captain at most once, on explicit request, per the Status Viewer's existing rules.

**Correctness hunt (Phases 2-3 spike step 3) — no guarantee is dropped by deferring past the greet.** Each guarantee carried by a deferred step is either (a) re-asserted as a state READ in `status --boot --json` so the greet stays accurate, or (b) an ACTION that is either kept before-greet (when a greet-and-stop boot is the only thing that would ever run it) or caught by the first event-loop pass / first dispatch (when a later trigger is guaranteed to fire before it matters):

- **Merged-PR advancement — KEPT before-greet (S7b), NOT deferred (corrects the earlier claim).** The earlier draft asserted this was "caught by Event-Loop step 1 + the pr-merge idle hook." That is FALSE for a greet-and-stop boot: the Event Loop fires only "after each agent completion" (`claude-first-officer-runtime.md` `## Event Loop`) and the idle hook fires only when "nothing is dispatchable" inside that same loop — a boot that greets and stops for input never enters the loop, so a merged PR would be REPORTED off live `pr_state` but never ADVANCED/archived. Fix: S7b runs the pr-merge startup-hook advancement before-greet, gated on the boot JSON `pr_state` showing a `MERGED` non-terminal entry (so it costs nothing on the common boot). This is the cheap-correctness-action-before-greet half of the dividing line.
- **Single-entity (`-p`) mode — S7b covers it too (closes M5).** The deferral originally dropped the workflow-wide startup-hook scan, and `-p` mode runs bare (no team), so the Event-Loop step-0 reconcile sweep's Class C is SUPPRESSED in bare mode (`internal/dispatch/reconcile.go` line 215 gates `classC` on `rosterTrusted`; a bare reconcile reports only git-only D/E). So neither the event loop nor the reconcile sweep would catch an off-target merged PR in `-p` mode. S7b is host-neutral and roster-independent — it reads `pr_state` from the same `status --boot --json` and advances merged PRs whether or not a team exists — so the `-p` boot advances merged PRs via the same before-greet sweep. (S7b runs in single-entity mode scoped consistently with that mode's entity scope; an off-target merged PR surfaced by the boot JSON is still advanced, since advancement is a correctness obligation, not new dispatch work.)
- **`gh`-absent boot — greet degrades gracefully (closes M6).** S7b and the greet's PR-state accuracy both rest on `status --boot --json`'s `pr_state` carrying LIVE merge state, which only happens when `gh` is on PATH: `internal/status/boot.go` `checkPRStates` returns status `"gh not available"` with NO entries when `gh` is absent, serialized as `pr_state.status == "gh not available"` (`internal/status/json_commands.go` line 170). When the FO reads that status, it MUST NOT claim any PR is merged or unmerged — S7b is skipped (no live state to act on, matching the pr-merge mod's own "If `gh` is not available, warn the captain and skip PR state checks") and the greet states PR merge status is UNKNOWN for PR-bearing entities ("{N} PR-pending entit{y/ies}; merge state unknown — `gh` not available") rather than reporting a stale or absent state as authoritative. This makes the greet's accuracy claim honest in both branches: live state when `gh` is present, an explicit unknown when it is not.
- **Other deferred guarantees:** orphan surfacing (the boot JSON's `orphans` array, before-greet); mod-block resume (Event-Loop step 2, a first-action obligation that only matters once dispatch resumes); supersede/teardown (vacuous at a shallow boot — no team exists to clean). **The other genuinely-cannot-defer step is the split-root halt-gate + pull-on-boot (S6/S7)** — already a before-greet shared-core step, part of the sequence, not an obstacle.

## Acceptance criteria

Each AC names an end-state property of the finished task, verified by something OUTSIDE this task body that can fail. **No AC is proven by a string/substring/regex match over any instruction file the model reads** — that is banned by this workflow and by `internal/contractlint/boundary_guard_test.go` (a passing match only asserts the implementer's own text is present; a valid paraphrase fails it and an inverted clause passes it). The behavioral ACs (AC-1, AC-2, AC-3) are live drives over durable on-disk state / the captured tool stream; AC-6 is the live MEASURED-saving drive (parsing the run's token stream). The two structural ACs are AC-4 (reference-closure — every deferred load-point the boot files name resolves to a real file on disk, the filesystem as oracle, via a NEW buildable `internal/contractlint` test) and AC-5 (the offline gate `go test ./...` stays green after the split, oracle = the test runner's exit code). The no-load-at-boot / frontmatter-only-read proof is NOT a structural grep — it is AC-1's live drive observing the actual read sequence and durable state. The set is AC-1..AC-6 (the cycle-2-dropped "AC-4(b)/AC-5" prose-grep stays dropped; AC-5 here is a different, real check — the offline-gate-green pin — and AC-6 is the measured-saving drive, both NEW this cycle).

**On the Phase-1 GUIDANCE content (the Operating-principles/ethos section, the `agents/first-officer.md` cross-reference drop):** this is behavior-shaping prose, NOT a testable acceptance criterion. Its proof is the existing live scenarios (AC-3) still passing + the high-stakes detached audit + gate review — there is no "ethos present" or "drift reduced" metric, because such a check would be either a banned prose-grep over the contract or a tautology. The ethos is real authoring work that ships with the split; it carries no AC of its own.
