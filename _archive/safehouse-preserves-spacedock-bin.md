A safehouse-wrapped `spacedock claude` / `spacedock codex` should keep using the binary that launched it. Today the launcher-injected `SPACEDOCK_BIN` is lost across the safehouse boundary, so every in-session helper call silently falls back to the `spacedock` on `$PATH`.

## Problem

The front door launches the host CLI with `SPACEDOCK_BIN` set to the launching binary (the launcher-command invariant: helpers prefer `$SPACEDOCK_BIN` over PATH). When the launch is wrapped by **safehouse**, the wrapper does not propagate `SPACEDOCK_BIN` into the sandboxed environment. Inside the session the variable is unset, so the FO/ensign helper calls (`status`, `dispatch build`, …) resolve `spacedock` from `$PATH` — which may be a different (released/stale) binary than the one under test.

Impact (HIGH for dev/test): a safehouse-wrapped dev launch appears to use the dev binary but actually drives the PATH binary. Behavior diverges silently — exactly the failure mode the launcher invariant exists to prevent. The current workaround is to `export SPACEDOCK_BIN=<dev binary>` before launching, which the operator must remember.

## Proposed approach

**Forward `SPACEDOCK_BIN` through safehouse with `--env-pass`** when (and only when) safehouse wrapping is active. The strip is on safehouse's side (`launchEnv` already sets `SPACEDOCK_BIN` on the outer `safehouse` process; safehouse sanitizes it out across its boundary). safehouse ships a launch flag for exactly this: `--env-pass NAMES` (comma-separated host-env var names forwarded on top of the sanitized defaults; compatible with default mode). It is a safehouse launch flag spacedock owns at the call site, like `--trust-workdir-config` — no safehouse profile/config change is needed.

Concretely: when `runClaude` / `runCodex` decide to wrap (`wrap == true`), add `--env-pass SPACEDOCK_BIN` to the safehouse flags (the `extra` slot, before the `--`), so the wrapped argv becomes

    safehouse --trust-workdir-config --env-pass SPACEDOCK_BIN [extra] -- claude --dangerously-skip-permissions --agent spacedock:first-officer …

(and the codex analog). The inner program directly after `--` stays `claude`/`codex` — NO `/usr/bin/env` wrapper, NO `SPACEDOCK_BIN=` token in the inner argv — so safehouse's program-keyed profile auto-detection still sees the real program and applies its profile. The flag is gated on the same `resolvedLauncherBin()` source `launchEnv` reads: it is added ONLY when the bin resolves (and ONLY on the wrap path). When `resolvedLauncherBin()` returns no binary (resolution failed), emit no `--env-pass` — never a stale pass-through (mirrors the existing `launchEnv` omit-on-failure behavior). The unwrapped launch inherits `SPACEDOCK_BIN` directly through `launchEnv`, so no flag there.

Why `--env-pass`, not an inner-argv `env SPACEDOCK_BIN=<bin>` prefix: prefixing the inner argv with `/usr/bin/env` changes the program safehouse sees from `claude` to `/usr/bin/env`, so safehouse's program-keyed profile auto-detection misses and the DEFAULT `spacedock claude` loses its claude profile (a ship-blocker the captain's real-safehouse run caught — only `--safehouse-enable all-agents` worked around it). `--env-pass` carries the value through the same sanitization boundary without touching the inner program, so the profile is preserved. (The safehouse-allowlist/profile-edit route the seed sketched is not the chosen path — spacedock does not own safehouse's profile schema; `--env-pass` is a launch flag, self-contained in the front door, that degrades safely when the bin can't be resolved.)

## Out of scope

- safehouse's broader sandbox model.
- The general PATH-fallback behavior when no launcher is involved (that fallback is correct).

## Acceptance criteria

- **AC-1 — Wrapped claude argv carries `--env-pass SPACEDOCK_BIN`.** A safehouse-wrapped `spacedock claude` launch carries `--env-pass SPACEDOCK_BIN` among the safehouse flags (before `--`), so safehouse forwards the launching binary through its env sanitization; the inner program is `claude` directly after `--`.
  *Verified by:* a `runClaude` oracle in `internal/cli/safehouse_frontdoor_test.go` asserting the exact wrapped `want` argv contains `--env-pass SPACEDOCK_BIN` before `--` and `claude` directly after `--`, with NO `/usr/bin/env`/`SPACEDOCK_BIN=` token in the inner argv (`TestClaudeSafehousePresentWrapsArgv`). Fails on a wrapped argv missing the flag.
- **AC-2 — Wrapped codex argv carries `--env-pass SPACEDOCK_BIN`.** The codex analog: a safehouse-wrapped `spacedock codex` launch carries `--env-pass SPACEDOCK_BIN` before `--`, with `codex` directly after `--`.
  *Verified by:* a `runCodex` oracle asserting the wrapped `want` argv (`TestCodexSafehousePresentWrapsArgv`).
- **AC-3 — Unwrapped launch is unchanged.** An unsandboxed launch (no `.safehouse`, no `--safehouse*`) carries NO `--env-pass` flag; `SPACEDOCK_BIN` still reaches the host through `launchEnv` as today.
  *Verified by:* `TestClaudeNoSafehouseLaunchesPlain` / `TestCodexNoSafehouseLaunchesPlainNoBypass` extended to assert the `--env-pass` token appears nowhere in the unwrapped argv, AND `TestClaudeFrontDoorInjectsResolvedLauncherBin` still passes (env path intact).
- **AC-4 — No `--env-pass` when the binary cannot be resolved.** When `resolvedLauncherBin()` returns no binary, the wrapped argv carries no `--env-pass SPACEDOCK_BIN` flag (never a stale pass-through), exactly as `launchEnv` omits the env entry today.
  *Verified by:* a `runClaude` oracle with `executablePath` stubbed to error (`withExecutablePath(t, "", err)`), asserting the wrapped argv has no `--env-pass` token (`TestClaudeSafehouseWrapsWithoutEnvPassWhenBinUnresolved`).
- **AC-5 — `--env-pass` forwards the value through an env-scrubbing wrapper end to end.** Driven through a fake `safehouse` that *scrubs* `SPACEDOCK_BIN` by default but HONORS `--env-pass SPACEDOCK_BIN` (forwards the named var from its host env), the in-session helper resolves to the launching binary, not the PATH `spacedock`.
  *Verified by:* a fixture smoke (`safehouse_env_smoke_test.go`) whose fake safehouse scrubs `SPACEDOCK_BIN` but re-exports it when `--env-pass SPACEDOCK_BIN` is in its args, and whose inner probe resolves via the real `spacedock_launcher` expression from `internal/dispatch/launcher_command.go` (exported as `dispatch.LauncherCommand()`). The smoke FAILS without `--env-pass` (scrubbed → PATH fallback) and PASSES with it (forwarded → resolves `<bin>`) — the regression-control subtest pins the without-`--env-pass` fallback so the oracle is non-trivial.
- **AC-6 — The wrapped inner program is the host, not a wrapper (profile-detection guard).** The wrapped inner argv's FIRST token after the safehouse `--` is the host program name (`claude`/`codex`), NEVER `/usr/bin/env` — so safehouse's program-keyed profile auto-detection sees the real program. This is the oracle that would have caught the inner-argv-prefix mechanism breaking the default claude profile.
  *Verified by:* `TestClaudeSafehouseWrapInnerProgramIsHost` / `TestCodexSafehouseWrapInnerProgramIsHost` asserting `argv[i+1]` after `--` equals the host name on both wrap paths.

## Spike — riskiest mechanism exercised first

The riskiest unknown was "which side strips the env, and is there a spacedock-owned fix?" Exercised before committing to the approach:

- **Bug reproduced live, in this very session.** The ideation ran inside a safehouse-wrapped FO session (`APP_SANDBOX_CONTAINER_ID=agent-safehouse`, `CLAUDE_CODE_AGENT=spacedock:first-officer`, `SAFEHOUSE_CLAUDE_VSCODE_MODE=reuse` present). In that session `SPACEDOCK_BIN` was **unset**, and `which spacedock` resolved `/opt/homebrew/bin/spacedock` → `…/Caskroom/spacedock/0.19.4/spacedock` (md5 `bb4a4c6d…`), a DIFFERENT binary from the dev build `…/spacedock-v1/spacedock` (md5 `6f68258a…`). The dispatch fetch commands therefore drove the released 0.19.4 binary, not the dev one — the silent divergence this task exists to kill, observed directly.
- **Strip side located = safehouse, not spacedock.** Spacedock's side is proven correct: `TestClaudeFrontDoorInjectsResolvedLauncherBin` asserts `launchEnv` sets `SPACEDOCK_BIN` on the launched (outer `safehouse`) process. Yet inside the sandbox many other vars survived (`PATH`, `HOME`, `SSH_AUTH_SOCK`, `EDITOR`, all `CLAUDE_CODE_*`, `SAFEHOUSE_*`) while `SPACEDOCK_BIN` did not — safehouse selectively drops it across its boundary.
- **Fix mechanism validated (throwaway probe, `/tmp/spike-spacedock-bin`).** With a fake `safehouse` that `unset`s `SPACEDOCK_BIN` then execs the inner argv: (A) env-only propagation → inner helper falls to PATH fallback (reproduces the bug); (B) prefixing the inner argv with `env SPACEDOCK_BIN=<bin>` → inner helper resolves `<bin>`. The value survives the scrub because it rides argv, which safehouse passes verbatim past `--` (AC-6 launcher smoke already proved the verbatim handoff). `/usr/bin/env` is present and portable; a single `VAR=val` token is one argv element, so host flags after it are unaffected; the unwrapped path needs no prefix.
- **No remaining unverified mechanism.** The implementation composes already-proven behavior: spacedock's env set (proven), safehouse's verbatim argv handoff (proven, AC-6), and the `env VAR=val` argv prefix (proven by the probe above). Implementation is fixture/unit-testable with no live safehouse required.
