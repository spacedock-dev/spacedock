The Claude-team lifecycle (~10 steps) is inlined in the FO contract (`first-officer-shared-core.md` + `claude-first-officer-runtime.md`), mixing **generic Claude-team-harness discipline** with **spacedock-specific decisions**. `claude-first-officer-runtime.md` is the single largest contract file (~8.8k tokens) and most of it is team mechanics. The ceremony is error-prone — this session the FO tripped the TeamCreate sequencing rule, the deferred-tool `SendMessage` hop, and the supersede-shutdown dance.

## Problem

The generic team-orchestration discipline has zero spacedock content but is welded into the spacedock FO contract, so: (a) it can't be reused by any other Claude multi-agent workflow; (b) it bloats the FO boot read; (c) the error-prone ceremony is spread across a long contract rather than concentrated in one tested place.

## Proposed approach

Two-layer split:

**Layer 1 → a `using-claude-team` skill (generic Claude-team-harness discipline, reusable, zero spacedock content).** Exact blocks lifted out of `claude-first-officer-runtime.md`, by current line range (ground-truthed 2026-06-04):

- **Team Creation** — `claude-first-officer-runtime.md:6-28` minus the spacedock tail. The generic part is the `TeamCreate`-first sequencing rule, the NAME_PATTERN naming convention, returned-`team_name` handling, the NEVER-delete constraint, the diagnostic-only startup probe, the TeamCreate recovery procedure, and the **TeamCreate failure recovery ladder** (fresh-suffixed → Degraded → captain). The spacedock tail at lines 26-28 (`In single-entity mode, skip team creation` and the `status --boot --json` / `--next-id` ID-style read) STAYS in the FO contract — it is spacedock dispatch/ID semantics, not team-harness.
- **Standing-teammate spawn mechanics** — the generic spawn/forward-verbatim pattern from `claude-first-officer-runtime.md:30-60`. CAVEAT: the spawn body is welded to `spacedock dispatch list-standing/spawn-standing/show-standing` helper calls (spacedock-specific). The GENERIC kernel here is thin — "spawn declared standing teammates before the first team dispatch; forward the Agent spec verbatim; fire-and-forget; first-boot-wins." The `spacedock dispatch` helper invocations and the `_mods/` declaration layout STAY in the FO contract. This block is the **weakest extraction candidate** — most of its text is spacedock helper wiring. Recommend leaving standing-teammate mechanics in the FO contract for v1 and extracting only if a second consumer appears (YAGNI). See revised boundary below.
- **Degraded Mode** — `claude-first-officer-runtime.md:130-160` (triggers / effects / captain-report template / cooperative-shutdown sweep). MOSTLY generic, with two spacedock seams: the `/spacedock bare` captain command (line 140) and the `spacedock dispatch build` bare-mode emission detail (line 146). Lift the team-harness behavior; keep the `dispatch build`/`/spacedock` seams as FO-side parameters the skill references abstractly.
- **Awaiting Completion** — `claude-first-officer-runtime.md:207-235` (the don't-prematurely-teardown decision procedure, the three-things-only completion-signal definition, the anti-patterns, the DISPATCH IDLE GUARDRAIL). FULLY generic — this is the most error-prone, zero-spacedock block. Cleanest extraction.
- **Terminal Team Teardown** — `claude-first-officer-runtime.md:237-248` (the bounded best-effort `TeamDelete` settle-then-attempt loop, attempt cap, `TERMINAL_TEARDOWN_BOUNDED` marker). FULLY generic team-harness discipline. The shared-core Merge-and-Cleanup step 10 (`first-officer-shared-core.md:226`) already declares "the settle interval, the cap value, and the marker emission are the adapter's" — the skill BECOMES that adapter realization. Cleanest extraction alongside Awaiting Completion.
- **SendMessage routing + deferred-tool ToolSearch hop** — the `ToolSearch(query="select:SendMessage")` schema-fetch-before-call mechanic. NOTE: this is NOT currently a standalone section in `claude-first-officer-runtime.md`; the `ToolSearch select:TeamCreate` probe is at line 9, and SendMessage routing is scattered (reuse path in `first-officer-shared-core.md:144`, shutdown sweeps). The skill consolidates the generic "team tools are deferred; ToolSearch their schema before first call" discipline into one place.

**Layer 2 → the FO contract stays, thin (spacedock-specific decisions only):**
- dispatch via `spacedock dispatch build` (the helper-output-forward-verbatim contract, `claude-first-officer-runtime.md:72-128`)
- reuse conditions keyed on spacedock stage semantics (stage-model match, worktree-state routing — `first-officer-shared-core.md:133-140`)
- reconcile Class A/B → teardown mapping (`claude-first-officer-runtime.md:256-262`) — the Class-A "lingering" and Class-B "superseded" drift classes invoke the skill's cooperative-shutdown call, but the reconcile classifier itself is the `spacedock dispatch reconcile` helper
- the `spacedock dispatch context-budget` probe (`claude-first-officer-runtime.md:162-183`)
- single-entity-mode dispatch, ID-style reads, the event-loop `status --next/--where` scheduling

**Integration mechanism (settled by spike — see `## Spike` below): `Skill(skill="spacedock:using-claude-team")` invocation, NOT an `@`-include.** The original draft said the FO contract would `@`-reference the skill. The spike disproved that exact mechanism: `@references/...` resolves ONLY relative to the referencing skill's own directory (locked by `TestUserSkillReferenceClosureResolves` in `skills/integration/skill_surface_test.go`: "The path captured in group 1 is resolved relative to the skill directory"). A cross-skill `@../using-claude-team/...` include is unverified AND would break that closure test. The proven cross-skill composition path is `Skill(...)` invocation — already exercised daily: `agents/first-officer.md` Boot Sequence loads the FO contract via `Skill(skill="spacedock:first-officer")`, and every ensign dispatch opens with `Skill(skill="spacedock:ensign")`. So the FO Team-Creation section invokes `Skill(skill="spacedock:using-claude-team")` at boot (before the first team-mode tool call) to load the generic lifecycle, then keeps only the spacedock decision points inline.

**Load-bearing nuance — why this is a SKILL, not a binary command:** team ops are Claude *tools* (`TeamCreate`/`Agent`/`SendMessage`), not shell commands, so the binary cannot own them (it can't call Claude tools). The binary already owns everything shell-able (dispatch build, reconcile, context-budget). So the missing abstraction is a *skill* sitting beside the existing binary helpers — NOT a new binary command. Do not attempt to push team-tool-orchestration into the binary.

**Cross-runtime decision (settled): a Claude-only `using-claude-team` skill. No Codex analog, no merged `using-agent-teams`.** Grounded in reading `codex-first-officer-runtime.md` (106 lines, entire file): the generic blocks this task extracts are ALL Claude-team-harness primitives that Codex does not have. Codex "does not expose Claude Code's `TeamCreate` registry" (line 7), has no `team_name` lifecycle to create/recover/tear down (line 38), no `SendMessage`, no Degraded Mode, no supersede-shutdown, no ToolSearch-deferred team tools. Codex's analog surface is `spawn_agent` / `send_input` / `wait_agent` / the mailbox — entirely different mechanics with ZERO shared substrate. A merged `using-agent-teams` skill with per-runtime sections would just be the two adapters concatenated under one roof with no shared generic core, because the team primitives do not overlap. And the Codex adapter is already thin (106 lines) with no inlined ceremony to extract — there is nothing on the Codex side this task simplifies. So: `using-claude-team` is Claude-specific by construction; the Codex FO runtime stays as-is. If a Codex team-mailbox discipline ever bloats enough to warrant its own skill, that is a separate task with its own ideation (YAGNI — it does not today).

**Revised boundary call (standing teammates stay in the FO contract for v1).** Per the per-block analysis above, the standing-teammate spawn block is ~90% spacedock helper wiring (`spacedock dispatch list-standing/spawn-standing/show-standing`, `_mods/` layout). Extracting it would drag spacedock content into the "zero-spacedock" skill or leave a stub. The clean, high-value extractions are the four FULLY-generic blocks: **Team Creation (TeamCreate + recovery ladder), Awaiting Completion, Terminal Team Teardown, Degraded Mode**, plus the consolidated **SendMessage/ToolSearch-deferred-tool** discipline. These are the error-prone, zero-spacedock blocks the captain's friction report named. Standing-teammate mechanics stay in the FO contract until a second consumer justifies the extraction.

## Spike

**Riskiest unverified mechanism: cross-skill content loading.** The design's soundness rested on the FO contract being able to pull a separate `using-claude-team` skill's content into the booting/dispatched FO's context. The original draft assumed an `@`-include. That is the load-bearing handoff — if it does not work, the whole decomposition fails (the generic content would be unreachable from the FO).

**Exercise run (smallest end-to-end check):** Surveyed every `@`-reference in the repo (`grep -rn "^@" skills/` → exactly two, both `@references/{file}` same-skill relative) and read the oracle that governs reference resolution (`skills/integration/skill_surface_test.go`, `TestUserSkillReferenceClosureResolves`). The test's own comment is authoritative: *"The path captured in group 1 is resolved relative to the skill directory."* Its `referenceRe` only ever resolves `references/...md` under the SAME skill dir, and it would FAIL on a dangling cross-skill path. Baseline confirmed green (`go test ./skills/integration/ -run TestUserSkill` → 3 passed).

**Result (part 1 — `@`-include disproven):** The `@`-include across skills is BOTH unverified (no in-repo precedent) AND actively incompatible with the existing closure oracle. So the integration mechanism must be `Skill(skill="spacedock:...")` invocation, not an `@`-include.

**Result (part 2 — the cross-skill `Skill()` handoff RUN AND DEMONSTRATED, not asserted).** Staff-review cycle 1 correctly flagged that the design's load-bearing handoff — *a running agent that has ALREADY loaded skill A invokes `Skill()` for skill B mid-run and receives B's body into its own live context* — was NOT actually exercised by the cited precedents. The frontmatter `skills: [...]` PRELOAD in `agents/first-officer.md:4` is a boot-time preload, and the ensign's `Skill(skill="spacedock:ensign")` is a freshly-dispatched WORKER's first action; neither is the mid-run A-then-B handoff. So I ran the real spike:

- I am an ensign that already loaded skill A (`spacedock:ensign`) at session start. Mid-run, I invoked `Skill(skill="spacedock:debrief")` (an already-registered skill, used purely as an inert probe — its instructions were not followed). **The full body of the debrief skill landed in my live context** — all four phases of its instruction text became visible immediately after the call. This IS the design's exact handoff: already-loaded-A → `Skill(B)` mid-run → B's body in-context. **PASS, demonstrated.**
- **Secondary finding (load-bearing for implementation):** a SKILL.md created DURING the session is NOT registered mid-session. I first wrote a throwaway `skills/spike-crossload-probe/SKILL.md` and invoking it returned `Unknown skill: spacedock:spike-crossload-probe` — the host's skill registry is built at session start and does not pick up newly-written skill files. **Implication:** the `using-claude-team` skill must SHIP in the plugin (registered before the FO session boots) — which it will, since it lives under `skills/`. It cannot be authored and consumed in the same session. The implementation's live-drive (AC-3) must therefore run a FRESH FO session against a build where `skills/using-claude-team/` already exists, not create-then-invoke within one session. (Throwaway probe skill removed after the spike.)

**Decision: the FO Team-Creation section invokes `Skill(skill="spacedock:using-claude-team")` at boot before the first team-mode tool call.** The mechanism is now demonstrated end-to-end, not inferred from the boot-preload precedents.

**Skill auto-discovery is proven:** `.claude-plugin/plugin.json` declares `"skills": "./skills/"`, so any `skills/{name}/SKILL.md` is auto-registered at session start. A new `skills/using-claude-team/SKILL.md` is discovered and invocable as `spacedock:using-claude-team` with no manifest edit — the same mechanism that registers the existing five user skills (locked by `TestUserSkillsPresentWithFrontmatter`). (Registration is at boot — see the secondary finding above: a fresh FO session is required for the new skill to be visible.)
