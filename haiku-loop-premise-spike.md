Test the riskiest, cheapest path first: a live Haiku-model FO drives ONE entity through the mechanical loop end to end — boot → dispatch a worker → review the report → advance → terminalize/merge — with NO tier self-identification, NO standing `level-3-judge`, NO gate-verdict escalation (all of that is deferred-72 / `kt-full`). The question is binary: can a weak model hold the contract loop at all?

If NO → the "Haiku-operable" goal and the tier bet (72) need rethink; `kt-full` stays shelved. If YES → `kt-full` (Haiku + L3 escalation) becomes worth running as the cut proof.

**Load-bearing residual — what a PASS does and does NOT license.** This drive exercises a ~25-line hand-authored mechanical loop over a stripped fixture, NOT the shipped FO contract. A PASS therefore licenses exactly: "the mechanical verbs (`boot`, `next`, `dispatch build`, `status --set` advance, `terminalize`+`archive`) are INDIVIDUALLY Haiku-drivable in order, so the must-build verb sequencing is sound." A PASS does NOT license "Haiku drives the shipped contract" — the full contract carries discovery breadth, gate judgment, tier self-identification, feedback cycles, and the real `spacedock claude` front-door, none of which this loop touches. Closing that gap — proving Haiku holds the REAL contract — remains `kt-full`'s burden. This spike de-risks the cheap-and-necessary precondition (the mechanics hold at all); it does not stand in for the full-contract proof.

The deliverable is checkable: a reusable live harness (build on `internal/ensigncycle/haiku_loop_spike_live_test.go`) **plus** the recorded, durable-state-graded result of running it. Grade on DURABLE STATE only — terminal `verdict:` frontmatter + the entity's committed status transitions — never transcript phrasing (README proof policy + 72's grading discipline).

## Problem

The whole layered-FO bet (sprint 0221, the tier-delegation member `72`, the deferred `kt-full` haiku drive) rests on one unproven premise: a weak model can RELIABLY drive the mechanical dispatch loop, needing help only on judgment. The archived w4 spike (`_archive/haiku-loop-spike.md`, PASSED N=3) measured the loop WITH the judgment layer attached — its `«gate»` step routed the verdict to a bare `Agent(model=opus)` L3 reviewer, and its load-bearing AC-3 graded gate-verdict PROVENANCE (did the verdict trace to the opus sub-call). That conflates two questions: "can Haiku follow the contract mechanics" and "does Haiku escalate the judgment correctly." This spike isolates the FIRST. If Haiku cannot even hold the mechanics — call the right binary verbs in order, produce the right durable state, never invent a step — then no amount of judgment-escalation machinery saves the tier bet, and `72`/`kt-full` are building on sand. That failure, if it exists, is the cheapest one to find: it needs no L3 wiring, no standing mod, no gate fixture.

The captain's load-bearing caveat from the w4 prelim findings (`spike-prelim-findings.md`) is the real product here: **Haiku reliability, not capability, is the open question.** Haiku passed these loops in earlier days and at some point became FLAKY. A single pass proves only that Haiku CAN hold the mechanics once; the spike measures whether it HOLDS them across N≥3 — and the must-hold signal is per-step cleanliness across all N, with any break on any run marking that step unreliable.

## Proposed approach

Drive a bare `claude --model haiku -p` FO through a STRICTLY MECHANICAL hand-loop over a throwaway split-root fixture, and grade the durable on-disk end-state. The harness already exists (`internal/ensigncycle/haiku_loop_spike_live_test.go` + its N-wrapper `haiku_loop_spike_n_live_test.go`); this spike STRIPS the judgment half out of it rather than building from scratch.

### The mechanical-only loop (what stays, what is cut)

The w4 hand-loop was `«boot» → «next» → «dispatch» → «state.commit» → «gate»(route-to-opus) → «merge»`. This spike's loop is `«boot» → «next» → «dispatch» → «advance» → «terminalize»` — the `«gate»` step (and its opus `Agent` sub-call, its VERDICT-provenance grade, the `gateVerdictFromL3`/`opusAgentSpawned` stream facts) is REMOVED. The fixture carries NO `gate: true` stage. "Review the report → advance" is a MECHANICAL FO step (read the worker's appended report, then `status --set` to the next stage), not a verdict. Haiku is never asked to make a judgment call, so there is nothing to escalate, nothing to route, no tier to self-identify.

### The minimal driving entity (the fixture)

A throwaway split-root fixture (same `internal/ensigncycle` isolated-temp-repo pattern) whose workflow has THREE non-gate stages so dispatch, advance, and terminalize are each DISTINCT observable steps:

```
implementation (initial)  →  integration  →  done (terminal)
       worktree: false         no gate            terminal
```

- `implementation` (initial, dispatchable) — the FO dispatches one bare-mode worker here via `spacedock dispatch build` + a bare `Agent(...)`. The worker appends a fixed marker line (`WIDGET-BUILT`) and a `## Stage Report: implementation` to the entity body. Marker presence is the proof the dispatched worker actually did work, not that the FO moved a frontmatter field.
- `integration` — a plain non-terminal, non-gate stage. The FO mechanically ADVANCES the entity here after the worker returns (`status --set <slug> status=integration` + a path-scoped state commit). This step is what makes "advance" distinct from "terminalize": a one-stage `implementation→done` fixture would collapse them and lose the observation.
- `done` (terminal) — the FO TERMINALIZES (`status --set <slug> status=done completed verdict=passed`), then ARCHIVES (`status --archive <slug>`), then makes a final path-scoped commit. The `verdict=passed` token is STRUCTURALLY REQUIRED, not a judgment: the status mutator's finalize guard (`internal/status/handlers.go:197` — "cannot be finalized (`completed`) without a verdict") refuses to write `completed` without a `verdict:` in the same call, and that guard keys on the FINALIZE ACTION, NOT on any `gate: true` stage (verified at `handlers.go:188` — "keys on the finalize action, NOT on `status==terminal` alone"). So the fixture has NO merge hook and NO gate stage, yet the terminal set still carries a `verdict:` because the binary requires it. The loop prescribes a FIXED token (`verdict=passed`); Haiku writes it mechanically, never adjudicates it. The deferred-tier vocabulary (`level-3`, `L3`, `### Gate Verdicts`) is absent from the fixture and the loop prompt entirely (consistent with the live-tree posture: `strip-deferred-tier-vocabulary` is actively removing that vocabulary from the shipped contract because `72` is deferred).

No `docs/dev` entity is ever driven; the drive runs only against the temp fixture (`t.TempDir()`), git-inited as two roots (definition root for the README, state checkout for path-scoped entity commits).

**AC-3 — Durable-state grading is specified to the exact field level: the terminal frontmatter AND the committed intermediate `integration` transition that prove the Haiku FO held the FULL loop (not a shortcut), gradable WITHOUT reading the drive transcript.**
The entity body pins the EXACT durable oracle (so a teammate can re-grade from disk without the stream): the terminal frontmatter fields and their anchored matchers (`status: done` via `^status:\s*done\s*$`; `completed:` non-empty; `verdict:` non-empty via `^verdict:[^\S\n]*\S`), the entity LOCATION (`_archive/<slug>.md`), the `WIDGET-BUILT` body marker, and — LOAD-BEARING — the committed status-transition trail.

The transition trail is graded by TWO distinct fields, not one:
- `pathScopedCommit` — at least one commit naming only the entity (`someCommitNamesOnly`). This proves the path-scoped commit discipline held.
- `integrationTransitionCommitted` (NEW, the BLOCKER fix) — the state-checkout git log contains a commit whose committed entity blob carried `status: integration`, AND the entity went through ≥2 path-scoped commits (the `implementation→integration` set, then the `integration→done`+archive set), with the MIDDLE one carrying `status: integration`. Concretely: `git -C {stateDir} log -G'^status: integration$' -- {slug}.md` returns at least one commit, AND `git log --pretty=@@COMMIT@@ --name-only` shows ≥2 commits naming only `{slug}.md`. This field FAILS if the Haiku FO jumped `implementation→done` (skipping the `integration` advance): such a run produces exactly ONE path-scoped commit (the terminalize) and NO committed blob ever carried `status: integration`, so `integrationTransitionCommitted=false` even though every OTHER field (`statusDone`, `verdictSet`, `builtMarker`, `pathScopedCommit`) passes.

This is why the field is mandatory: WITHOUT it, the 3-stage fixture's whole purpose collapses. `someCommitNamesOnly` returns true on the FIRST path-scoped commit it finds (verified at `liveassert_test.go:84` — `flush()` returns true on a single-file commit), so a skipped advance satisfies it; `statusDone`/`verdictSet`/`builtMarker` all read the TERMINAL state, which a shortcut also reaches. The intermediate-transition assertion is the ONLY field that distinguishes "held the full loop" from "skipped to the end and still produced a clean terminal." A Haiku FO that defeats the fixture by collapsing `implementation→done` MUST fail the AC-3 grade.

The terminal `verdict:` is graded ONLY as "set to the loop-prescribed FIXED token (`verdict: passed`)" — a STRUCTURALLY-REQUIRED mechanical write the finalize guard (`handlers.go:197`) forces, explicitly NOT an adjudicated value. This is the precise distinction from w4: w4 graded verdict PROVENANCE (did the value trace to an opus L3 sub-call); this spike grades verdict PRESENCE (was the required token written), with no provenance claim because there is no L3 to trace to.
Verified by: the durable-oracle specification in the body matching the harness's grade implementation field-for-field (the grade struct's durable fields ↔ the listed frontmatter/location/marker/commit facts, INCLUDING `integrationTransitionCommitted`), demonstrated by the harness reproducing the grade from the archived fixture + git log with the stream discarded; AND by a negative check — a fabricated "skipped-advance" git history (one terminalize commit, no `status: integration` blob) grades `integrationTransitionCommitted=false`, proving the field is load-bearing.
