The contract binds runtime-varying capabilities as `«fn»`s: `fo-dispatch-core.md:83` — "Runtime adapters bind the capability `«fn»`s below in their `## Runtime implementation` blocks." Present/absent and async/blocking are resolved per adapter (`«addressable-worker»` :91, `«async-dispatch»` :96). But some CORE-LEVEL prose asserts a runtime behavior FLAT — as if universal — which contradicts what a given adapter actually binds. An FO reading the core trusts a guarantee its runtime does not provide, and either acts wrongly or has to improvise the gap by judgment.

## Two known instances (both caught in the field, not by a check)

1. **Standing-teammate idempotency (entity g6).** `fo-dispatch-core.md` describes standing-teammate injection as "Idempotent (already-alive members omitted)"; `claude-fo-dispatch.md` says the call "does NOT dedup … idempotency is your own-roster concern — do not re-inject a standing teammate you already spawned." Both cannot hold. Observed: the 0260 Commander FO received a spawn spec for an already-alive teammate and "had to decide by judgement," deferring to point-of-need — a call the contract should have made for it.

2. **Async/streaming fan-out.** The v4dm fan-out clause draft asserted a "streaming per-member verify" as the universal failure mode, but streaming only exists when `«addressable-worker»` is PRESENT / `«async-dispatch»` is ASYNC; in bare mode dispatch BLOCKS and reviews batch automatically. The clause WORDING is fixed in v4dm (streaming now bound to `«async-dispatch»`). The RESIDUAL, deeper gap this entity owns: a Claude FO in bare `claude -p` (`«addressable-worker»` ABSENT) authored an async streaming fan-out — "member 1's findings verify while member 27 is still being read" — a shape its own runtime cannot execute. The FO planned against a capability it does not have; nothing in the contract stopped it.

## Problem shape

Both are the same class: a core-level claim about runtime-varying behavior that a binding contradicts (instance 1) or that an FO applies without checking its own binding (instance 2). The `«fn»` mechanism exists precisely to localize runtime variance; these leak it back into flat core prose or into FO planning that ignores the binding.

## Proposed approach (firmed at ideation, spike-validated)

1. **Relocation rides existing machinery.** `internal/contractlint/capability_binding_test.go` already defines the migration path: `runtimeBoundCapabilities` (currently `worker.spawn`, `worker.shutdown`) marks capabilities whose per-host binding lives in the adapters, with `runtimeBoundArrowViolations` enforcing that their core blocks are host-neutral (kind-only `→ **runtime-binding**` arrow, no host word in any form). The fix for the six remaining `→ Claude:/Codex:/Pi:` lines (`fo-dispatch-core.md:94/:98/:104/:108/:119/:123` — «addressable-worker», «async-dispatch», «worker-identity», «completion-signal», «context-budget», «roster-reconcile») is: add the six names to `runtimeBoundCapabilities`, replace each arrow with the kind-only pointer, and move the small non-redundant residue into the adapters. Spike-measured: most of the Claude coverage was ALREADY duplicated in `claude-fo-dispatch.md`, so relocation is largely deletion; Pi receives ~416 bytes of genuine residue (interrupt-steering, cwd-on-every-call, advisory detail, model-space ownership), Codex receives zero (its `## Runtime implementation` already bound everything).
2. **The standing guard is a contractlint CONTAINMENT check (captain directive 2026-07-21)**: a new `internal/contractlint/host_neutral_core_test.go` asserting the five shared files (`first-officer-shared-core.md`, `fo-dispatch-core.md`, `fo-write-core.md`, `fo-merge-core.md`, `ensign-shared-core.md`) carry no host name (`claude|codex|pi|opus|sonnet|haiku|fable`, word-bounded, case-insensitive — the same `hostWordRe` shape `capability_binding_test.go:39` already uses) and no host tool token (enumerated: `Agent(`, `SendMessage`, `TeamCreate`, `TeamDelete`, `task_notification`, `run_in_background`, `subagent_type`, `ToolSearch`, `BashOutput`, plus the Codex/Pi token vocabularies already enumerated in `runtime_binding_block_test.go:224-241`). Existence-fact containment, same species as `TestRuntimeToolTokensStayInBindingSections` — `toolTokenContainmentViolations` is directly reusable. Excluded from the token set, with grounds: generic harness verbs every host exposes (`Bash`, `Read`, `Grep`, `Write`, `Edit`, `Skill`) and spacedock's own cross-host dispatch-prompt convention (`Skill(skill="spacedock:ensign")`, emitted by `internal/dispatch/build.go` for every host). Discriminator control: planted host word and planted tool token each red on a clean body; `pi`-lookalike words (`api`, `spike`, `pickup`) pass.
3. **Sweep + reconcile the flat claims** — the enumerated table is in `## Flat-claim enumeration (AC-2)` below: 15 rows, 3 semantic CONFLICTs (two previously unknown), the rest containment leaks. Two seed instances resolved per AC-3.
4. **Redefine the budgeting helper (captain scope addition 2026-07-21).** `foPromptMetrics` (fo_function_reference_invariant_test.go:51) sums all 13 `foFunctionReferencePaths` — double-counting all three host adapters plus every deferred core, a load no single FO ever pulls. Replace with per-host load sets: `load(H) = SKILL.md + shared cores (dispatch/write/merge) + H's adapter file(s) + the trigger skills reachable on H` (present-gate and feedback-rejection-flow on all hosts; using-legacy-claude-team and fo-dispatch-recovery on Claude only). Ratchet each host against its OWN baseline (three constants, not max-only — a Codex-only regression must not hide under Claude headroom); the checkpoint logs all three; the mutable-address lint keeps the 13-file union. Measured today: the sum (122960) overstates the real worst-case host load (Claude, 111128) by 11832 bytes (~9.6percent) and overstates Codex/Pi by ~48k/~52k — the old ceiling's byte margin was an artifact of the double-count, and the 87-byte figure was additionally stale (today's measured margin under the old metric is 363).

## Out of scope

Re-adding BEHAVIORAL phrase/prose checks — a grep asserting what a program or agent DOES (the banned shape). The AC-1 containment check is the permitted kind: it asserts an existence/structural fact (a host name's presence in a shared file), which the captain's grep ruling explicitly allows and which existing contractlint already does for token containment. Also out of scope: changing any host's actual runtime policy — this reconciles the DESCRIPTION with the binding, it does not change what a runtime does. Not a 0.26.0 blocker: both instances are pre-existing, and instance 2's wording is already corrected in v4dm.
