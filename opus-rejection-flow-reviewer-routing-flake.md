`TestLiveClaudeSharedScenarios/rejection-flow` failed on the **claude-live opus** lane (CI-E2E-OPUS) of PR #409's run 27861449587 (`claude_live_runner_test.go:122`) with the assertion `assertClaudeSingleEntityRejectionFlow` reporting "the cycle-2 re-review was routed to an implementation worker (`spacedock-ensign-rejection-task-implementation`)."

**Root cause (verified — a TEST FALSE-POSITIVE, not opus model-variance, not a routing bug):** grading the original failing CI stream (run 27861449587 att1, artifact 7762522843) plus three fresh isolated live opus runs shows opus ALWAYS routes the cycle-2 re-review to a VALIDATION worker — never the implementation worker. The opus FO drives the headless `-p` session in TEAM mode (named background workers) and reaps each superseded cycle worker with a `shutdown_request` SendMessage to its `…-implementation` handle, exactly as the supersede-shutdown contract requires. The assertion flagged ANY SendMessage whose `to` contained "implementation" — without inspecting the body — so it misclassified that mandatory cooperative teardown as a re-review routing. Sonnet passed the same commit only because it drives BARE mode (no named workers to reap → no SendMessage to an impl handle), so only opus tripped the body-blind check. The deliverable is the assertion fix (body-aware impl-handle check + team-aware validation-spawn premise), not a contract/prose change.

## 0230 — why this is in the stable-cut sprint
The `v0.23.0` tag fires only on a GREEN Runtime Live E2E run (the `e2e-gate`). A flaky `rejection-flow` lane (this entity) makes that green run a coin-flip at cut time — a red here blocks the tag or forces a waiver. Establishing the opus frequency (AC-1) and fixing the false-positive (AC-2) de-risks the e2e-gate that gates the cut. This is a live-lane reliability member, not a byte-gate member.

## Resolution
The opus/sonnet asymmetry is bare-vs-team dispatch mode plus a body-blind substring check in the test, not a model-comprehension gap in the contract. `assertClaudeSingleEntityRejectionFlow` is corrected to (1) exempt `shutdown_request` bodies from the impl-handle violation check — only a non-teardown re-review/validate instruction to the fix worker is the violation; and (2) accept BOTH contract-valid `-p` end-states — bare mode's two fresh validation spawns OR team mode's one spawn plus a reuse message to the kept-alive `…-validation` reviewer.
